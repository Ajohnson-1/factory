# Phase 2.1 — Keep agents away from `.env` (container isolation)

**Goal:** factory agents never see orchestrator secrets. Each agent session runs in an
ephemeral Docker container that can only see its worktree + the LLM provider key it
needs. `.env` (TRELLO_*, DISCORD_*, GITHUB_TOKEN, WEBHOOK_SECRET) stays on the host,
in the orchestrator process only.

**Decision (confirmed):** container isolation — one `docker run` per agent session.
This is what pi's security docs recommend as the strongest practical boundary:
"Entirely inside a container, virtual machine, or sandbox — host files and processes
that you do not expose to the environment."

## Threat model (what leaks today)

| Vector | Today | After 2.1 |
|---|---|---|
| `process.env` | In-process `createAgentSession` inherits the full orchestrator env; agent can `printenv`/`env` via its bash tool | Container gets only an allowlisted env (LLM key, PATH, HOME) |
| Files | Agent runs as the factory OS user; can `cat <repo>/.env` by absolute path | Only the worktree (rw) and the repo's `.git` (ro) are bind-mounted; the rest of the host FS is invisible |
| Git worktree | `.env` is untracked so worktrees don't contain it (good — keep it that way, tested) | Same, plus asserted in tests |
| Network | Agent can reach anything | Unchanged (accepted risk, documented); optional proxy egress later |

**Boundary rule:** the container is the trust boundary. Everything on the host
(orchestrator, `.env`, Trello/GitHub/Discord clients, push + PR creation) stays outside.
The one deliberate exception is the repo's shared `.git`, mounted **read-only** because a
git worktree is useless without it — and the runner refuses to start a container whose
git config embeds a credential, since that file is now part of the agent's view.

## Architecture

```
host (orchestrator, keeps ALL secrets)
├── worker/queue.ts        unchanged
├── worker/runner.ts       agent step becomes: runAgentInContainer(worktreeDir, prompt, onEvent)
└── after agent exits: host `git add/commit` + `git push` + Octokit PR (needs GITHUB_TOKEN — never in container)

container (ephemeral, per agent run)
├── image: factory-agent (node:22-slim + pi CLI + git/ripgrep, non-root user)
├── mounts: <worktree>:/work (rw)  +  <repo>/.git:<repo>/.git (ro, for git log/diff/status)
├── env:    PATH + HOME + set provider API keys   (only)
└── cmd:    pi --mode json --no-approve -- "<prompt>"   → NDJSON events on stdout
```

Event streaming to Discord is preserved: pi's JSON mode writes newline-delimited
session events on stdout; the host parses them and maps
`tool_execution_start`/text deltas to the existing progress embeds (same mapping the
in-process `session.subscribe` did).

## Steps

- [x] **1. Agent image.** `deploy/docker/factory-agent.Dockerfile`:
  ```dockerfile
  FROM node:22-slim
  RUN npm i -g @earendil-works/pi-coding-agent
  RUN useradd -m agent
  WORKDIR /work
  USER agent
  ENTRYPOINT ["pi"]
  ```
  Plus `deploy/docker/build.sh` (`docker build -t factory-agent ...`) and a CI job /
  VPS deploy step that builds it.

  Built as written, plus what it actually needs: `bash ca-certificates git ripgrep`
  (pi's documented image installs them; `node:22-slim` ships no git), a
  world-writable `HOME` so `--user <host uid>` works, and
  `git config --system --add safe.directory '*'`. `build.sh` pins `PI_VERSION` from
  **package-lock.json**, not the caret range — see deviations.
- [x] **2. Env allowlist builder** — `src/agent/env.ts` (pure, unit-testable):
  ```ts
  const PROVIDER_KEYS = ["ANTHROPIC_API_KEY","OPENAI_API_KEY","GEMINI_API_KEY",
                         "GROQ_API_KEY","OPENROUTER_API_KEY","MISTRAL_API_KEY"];
  export function buildAgentEnv(): Record<string,string> // PATH, HOME + set provider keys
  ```
  Only provider keys that are actually set are passed. No TRELLO/GITHUB/DISCORD/WEBHOOK vars, ever.
  Implemented with an injectable `source` (`buildAgentEnv(process.env)` by default) and
  **container-side** `PATH`/`HOME` constants — inheriting the host `HOME` would point
  pi's config dir at a path that is not mounted.
- [x] **3. Container runner** — `src/agent/container.ts` (pure arg builder + spawner):
  ```ts
  export function buildDockerArgs(worktreeDir: string, prompt: string): string[]
  // ["run","--rm","-v",`${worktreeDir}:/work`,"-w","/work",
  //  "--cap-drop=ALL","--security-opt","no-new-privileges","--init",
  //  ...envArgs(image, buildAgentEnv()),
  //  "factory-agent","--mode","json","--no-approve",prompt]
  export async function runAgentInContainer(worktreeDir, prompt, onEvent): Promise<{ok:boolean; text:string}>
  ```
  - `--no-approve`: skip untrusted project resources (`.pi/` in the target repo) —
    non-interactive modes can't show the trust prompt, and factory worktrees are
    untrusted input.
  - Spawns `docker` with `spawn(..., { stdio: ["ignore","pipe","pipe"] })`, parses
    NDJSON from stdout line-by-line, forwards mapped events to `onEvent` (→ Discord
    progress embeds), collects the final assistant text, resolves on `agent_settled`.
    stderr → logs. Non-zero exit or error stop-reason → `{ ok: false, text }`.

    Three corrections from the pi source (0.84.4), see deviations: LF-only framing
    instead of `readline`, resolution on child `close` rather than `agent_settled`,
    and `--` before the prompt.
  - Also mounts `<repo>/.git` read-only (without it the agent has **no git at all**)
    and refuses to start if that `.git`'s config embeds credentials.
- [x] **4. Runner refactor** — in `src/worker/runner.ts`, replace the in-process
  `createAgentSession` block with `runAgent(worktreeDir, prompt, onEvent)` injected via
  the deps seam added in 2.0:
  - `AGENT_RUNTIME=container` (default) → `runAgentInContainer`
  - `AGENT_RUNTIME=process` (local dev without Docker) → old in-process path, kept as
    `src/agent/in-process.ts` (dev convenience only, documented as NOT secret-safe).
  - Push + `createPR` stay on the host in `runner.ts` — the container never needs git
    push credentials.

    Required one more host-side step: the agent can no longer commit (`.git` is
    read-only), so `runCard` calls `commitWork(dir, "factory: <card>")` before pushing
    and fails the job when the agent changed nothing. `buildAgentPrompt` tells the
    agent not to commit.
- [x] **5. Host hardening** (deploy):
  - `chmod 600` the orchestrator's env file in the systemd deploy script.
  - Move env file out of the repo tree on the VPS (e.g. `/etc/factory/factory.env`)

  - README: `chmod 600 .env` guidance for anyone running locally.

    Done, plus: `deploy/setup-factory.sh` now installs `docker.io`, waits for

## Deviations — what verifying instead of assuming changed

1. **Mounting only the worktree leaves the agent with no git.** A `git worktree` dir
   is not a repository: its `.git` is a one-line file (`gitdir: <repo>/.git/worktrees/<id>`).
   Verified in Docker: with the plan's single mount, `git log`/`git status` both die with
   `fatal: not a git repository: /private/tmp/.../repo/.git/worktrees/wt-card1`. Fix:
   a **second, read-only mount of the shared `.git`** at its own absolute path, which
   makes `log`/`diff`/`status`/branch work and leaves commits impossible
   (`fatal: Unable to create '.../index.lock': Read-only file system`). Consequences:
   the host now commits (`commitWork`) before pushing, `buildAgentPrompt` tells the
   agent not to commit, and because `.git` is in the agent's view the runner scans its
   config and refuses to spawn if a remote URL embeds a token.
2. **pi JSON mode always exits 0**, even when the provider request failed — the
   `stopReason` check in `runPrintMode` lives inside `if (mode === "text")`. So
   `ok:false` cannot come from the exit code alone; the collector watches
   `message_end.message.stopReason === "error" | "aborted"` and its `errorMessage`.
3. **Not `node:readline`.** pi's own docs: "Node.js `readline` is not suitable for this
   stream because it also recognizes those Unicode separators [U+2028/U+2029]." Those
   are legal inside JSON strings, so the reader is a byte-level LF splitter — with a
   test that puts U+2028 inside an assistant message.
4. **Resolve on child `close`, not on `agent_settled`.** `agent_settled` means pi has no
   automatic work left, not that the container is finished — resolving there would drop
   the exit code and the tail of the stream. A `spawn` failure also resolves (Node does
   not promise `close` after `error`), so a missing docker binary fails the job instead
   of parking the single worker slot forever.
5. **`--` before the prompt** (pi: `pi [options] [--] [@files...] [messages...]`), so a
   prompt that starts with `-` cannot be read as a flag. This needs pi ≥ 0.84.3 —
   verified: 0.84.2 rejects it with `Error: Unknown option: --`. Hence `build.sh` pins
   `PI_VERSION` from **package-lock.json** rather than the caret-stripped range, so the
   image always matches the pi the orchestrator is built and tested against.
6. **`buildAgentEnv` returns container-side `PATH`/`HOME`, not the host's.** `docker run`
   starts from the image's own env, so forwarding the host `HOME` would only point pi's
   config dir at a path that is not mounted.
7. **The deploy unit contradicted itself.** `ProtectHome=true` makes `/home`
   inaccessible and, unlike `ReadOnlyPaths=`, nothing can be re-exposed inside it — so
   the previous `ProtectHome=true` + `ReadWritePaths=/home/pi` hid the service's own
   `/home/pi/factory`. Now `ProtectHome=read-only` with the same `ReadWritePaths`.
   Also: `Requires=docker.service`, `EnvironmentFile=`, `SupplementaryGroups=docker`
   (the read-only-path options do not block AF_UNIX connections, so `/run` stays
   unwritable).
8. **The nftables egress filter does not cover agents.** Container traffic is *forwarded*
   through docker's bridge, not locally generated by uid `pi`, so the `meta skuid` rules
   never see it. Documented rather than silently claimed as protection.
9. **Provider keys are required in the env, not OAuth.** pi resolves a model from an env
   key automatically (verified against `defaultModelPerProvider` + "first available model
   with valid API key"), but `~/.pi/agent` is deliberately never mounted — that file
   holds the operator's own credentials. Without a key: `No API key found for the
   selected model`, exit 1.

## Notes / risks

- **Network egress is not restricted** by this phase (agent needs npm etc. while
  working). Document as accepted risk; follow-up option: docker network proxy that
  only allows the LLM provider + package registries. Note the deploy script's
  uid-based nftables filter does **not** constrain containers (forwarded traffic).
- **Image freshness:** rebuild `factory-agent` on pi package bumps (deploy script + CI).
  `build.sh` pins the exact version from `package-lock.json`, and CI builds the image on
  every push, so a bump that breaks the container fails a check instead of the first card.
- Container CPU/memory limits: add `--memory`/`--cpus` from config as a follow-up if
  parallel agents (2.2) show pressure.
- **A committed `.env` is not protected.** Untracked files never reach a worktree
  (guarded by `test/worker/no-env.test.ts`), but anything the target repo tracks ships
  with it — into the worktree, the container and the PR. That is the repo's own problem,
  not something a mount choice can fix.
- **The agent no longer commits.** It edits files; the host commits with
  `factory: <card name>` and fails the job on an empty working tree. Keeps write access
  to git metadata entirely outside the trust boundary.
- **`docker` must be installed and reachable by the service user** (docker group).
  `scripts/dry-run.ts` still exercises the in-process runtime, because a laptop has no
  image; the container path is covered by `TEST_DOCKER=1 npx vitest run test/integration`.
