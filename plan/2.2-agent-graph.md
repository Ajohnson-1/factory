# Phase 2.2 — Agent graphs: orchestrator agent + parallel worktree agents

**Goal:** for each card, an **orchestrator agent** decides at runtime which specialist
agents to run and fans them out **in parallel**, each in its own git worktree
(containerized per Phase 2.1). The orchestrator holds no write tools — it reads the
repo, plans, spawns, and merges results back into the card's branch.

**Decision (confirmed):** dynamic graph via an orchestrator agent with a `spawn_agent`
custom tool (pi SDK `customTools` + in-process `createAgentSession` for the
orchestrator itself — it runs on the host, read-only, and never needs secrets).

## Roles (registry)

| Role | Purpose | Tools | Worktree |
|---|---|---|---|
| `orchestrator` | Reads card + repo, decomposes, spawns children, verifies merged result | read-only (read/grep/find, no edit/bash) + `spawn_agent` | shared base worktree `wt-<card>` |
| `spec-writer` | Turns the card into a concrete spec (`factory-spec.md` in repo root) | read + edit/write | shared base (single writer, orchestrated) |
| `researcher` | Explores repo + (optional) web; writes `factory-research.md` | read-only + web | shared base (single writer, orchestrated) |
| `coder` | Implements one scoped task | full coding tools | **detached** `wt-<card>-c<n>`, branch `factory/<card>/c<n>` — N in parallel |
| `verifier` | Runs the repo's test suite / build on the base after merges; reports failures | read + bash (no write) | detached (throwaway) |

`verifier` is the extra role beyond the requested set — it's cheap (mostly
deterministic) and catches "parallel coders broke the build together". The
`reviewer` role (Phase 2.3) is registered here too but wired separately.

Role config is **data**, in `src/agents/roles.ts`:
`{ id, systemPrompt, tools | excludeTools, maxTurns?, worktree: "shared" | "detached" }`.

## Branch & merge design

```
origin/main
   └── factory/<card>                      ← base branch (the PR branch, as today)
         ├── factory/<card>/c1  (coder 1)  ─┐ merged back into base on success
         ├── factory/<card>/c2  (coder 2)  ─┤ (git merge --no-ff, on host, serially)
         └── factory/<card>/c3  (coder 3)  ─┘
```

- Base worktree `wt-<card>` (branch `factory/<card>` from `origin/main`) is created by
  the runner exactly as in MVP; orchestrator + spec-writer + researcher work in it.
- Each detached child gets `wt-<card>-<runId>` from the current base HEAD.
- On child success the host merges its branch into the base **serially**
  (concurrent merges into one worktree are unsafe). On merge conflict: worktree +
  branch cleaned up, and the tool **returns the conflict as an error to the
  orchestrator**, which re-plans (e.g. re-spawn the task with "task c1 already
  changed X — adapt"). This keeps conflict resolution inside the LLM loop, not in code.
- The `spawn_agent` tool returns a **summary** to the orchestrator: child role,
  success/failure, last assistant text (truncated), `git diff --stat` vs base, merge
  result.

## Concurrency & limits

- `MAX_PARALLEL_AGENTS` (default 4): the spawn tool caps concurrent container runs
  (simple semaphore); excess spawns queue.
- `AGENT_TIMEOUT_MS` (default 20 min) per child; on timeout the container is killed
  (`docker kill`), worktree removed, error returned to orchestrator.
- `MAX_AGENT_RUNS` per card (default 12) — hard budget so a looping orchestrator
  can't burn money; orchestrator is told the budget in its system prompt.

## Notes / risks

- **Orchestrator model cost:** it's a long-lived session; consider a cheaper/faster
  model via `model` session option if token burn shows up (config knob to add later).
- **File-scope conflicts** are handled by retry-with-context, not by file locking —
  good enough for MVP-scale cards; document it.
- Base worktree is shared by 3 roles — the orchestrator's prompt must serialize
  spec-writer/researcher (they're single-writers by design).

## Decision — orchestrator runtime (resolved 2.2 kickoff)

The step 4 sketch ("orchestrator runs in-process on the host, it holds no write
tools") was rejected: `excludeTools` removes tools from the model's reach, not
from the process, and an in-process pi session inherits the orchestrator's whole
`process.env` plus its filesystem — the exact exposure phase 2.1 exists to remove.

**Chosen: Option A — the orchestrator runs in a container like every other role,
and its `spawn_agent` custom tool reaches back out to the host over IPC.** Children
are started by the host, which is the only place with git write access anyway.

## Spike — Option A mechanics, verified on the real image (pi 0.84.4, 25s run)

Harness: a `spike_wait` extension tool + a token-checked TCP server on the host,
driven by the local vmlx model through the real `factory-agent` image. Findings,
with the evidence that produced them:

| Question | Answer | Evidence |
|---|---|---|
| Do `-e` extensions load under `--mode json --no-approve`? | **Yes.** `--no-approve` only sets `projectTrustOverride=false` (`dist/cli/args.js:218`) — it skips *project* `.pi/` files. An explicit `-e` is a command-line extension and registers normally. | `extension_loaded` then the model called the tool |
| Can a custom tool run long-lived? | **Yes.** No tool timeout exists in pi — the only timeouts are provider HTTP idle ones (`dist/core/http-dispatcher.js`). | 25 s tool: `elapsed: 25030ms`, agent then replied `DONE` |
| Do sibling tool calls run in parallel? | **Yes.** | two 3 s calls started 9 ms apart and both ended ~3.02 s later — serial would have been ~6 s |
| Can the container reach the host? | **Yes**, via `--add-host=host.docker.internal:host-gateway` + a host listener on `0.0.0.0` (loopback-only is unreachable through the gateway on Linux). | `authorized=true`, `hostPid` returned in the tool result |
| Does `defineTool` need importing? | **No — it is an identity function** (`dist/core/extensions/types.js:17-19`). Pass the plain object to `pi.registerTool()`. Only `Type` needs an import. | read of installed dist |

**The gotcha that decides where the extension lives.** A mounted extension resolves
its imports from its own directory upward, and `@earendil-works/pi-ai` is *not* in
the global root — it is nested at
`$(npm root -g)/@earendil-works/pi-coding-agent/node_modules/@earendil-works/`. From an
arbitrary mount point the import fails `ERR_MODULE_NOT_FOUND`; from inside the
package tree it resolves. So the extension is **baked into the image** next to a
`node_modules` symlink shim rather than mounted at run time — which also keeps
`buildContainerMounts`' "exactly two mounts" property (worktree + `.git`) intact,
and keeps extension code pinned to the image's pi version the same way `build.sh`
pins pi itself.

**Never write to stdout from an extension in JSON mode** — stdout *is* the event
protocol. Diagnostics go to stderr (the collector ignores it).

**Not yet verified:** real orchestrator-driven fan-out over a git workflow (the
smoke script), and behaviour under `--user` with a baked `/opt/factory` path.

## Spike 2 — the tool-model problem (`--tools` kills custom tools)

Step 4 says "verify exact built-in tool names at implementation time". Verified,
and it turned into a blocker with a non-obvious workaround:

- Extension/custom tools are **active by default**: at `session_start` the set was
  `read, bash, edit, write, probe_only` with no CLI flag passed.
- `--tools/-t` is an **allowlist that replaces** the active set
  (`sdk.js:144`: `options.tools ?? defaults`, then `.filter(excludeTools)`), and it
  **drops extension tools even when they are named in it**. With
  `-t read,grep,find,ls,spike_wait` the model reported only
  `read, grep, find, ls` and refused the call. So `--tools` cannot express
  "read-only built-ins **plus** `spawn_agent`".
- `pi.setActiveTools([...])` called from a `session_start` handler **can**: it took
  the set from `read,bash,edit,write,probe_only` to `read,grep,find,ls,probe_only`
  — custom tool kept, every writable built-in gone.
- `setActiveTools()` must not be called from the extension factory: extensions can
  be loaded without a session and pi fails startup with `"Extension runtime not
  initialized. Action methods cannot be called during extension loading."`

**Consequence for the design:** the orchestrator's tool policy is owned by the
extension, not by docker argv — the host passes the desired active set to the
container as data (`FACTORY_ACTIVE_TOOLS`) and the extension applies it at
`session_start`. Roles with no custom tool (coder/verifier/spec-writer) keep using
plain `--exclude-tools`, which is safe because they have nothing to lose.

**Verified flag spellings** (0.84.4 `dist/cli/args.js` + `--help`): `--system-prompt
<text>`, `--append-system-prompt` (repeatable), `--model <pattern>` (accepts
`provider/id` and `:thinking`), `--provider <name>`, `--tools/-t`,
`--exclude-tools/-xt`, `--no-context-files/-nc`, `--offline`.

**Host→container reachability differs by platform**: a host listener bound to
`127.0.0.1` IS reachable from a container via `host.docker.internal` on Docker
Desktop (verified: `{"reached":true,"via":"loopback"}`), but on Linux
`host-gateway` arrives at the bridge address, so the default bind stays loopback
and widening it has to be an explicit deploy choice — the per-run token is then the
only thing gating an endpoint that can start containers.
