# Phase 2.5 — Multiple repositories (one board + one channel per repo)

**Goal:** the factory serves N repos. Each has its own Trello board, its own
GitHub repository and clone, and its own Discord channel. Moving a card to Ready
on board *B* builds in clone *B* and reports in channel *B*.

Depends on **2.4**. The per-board routing this phase needs is the same mechanism
as parsing Trello's real payload: both require reading a board id off an event,
which the current `TrelloWebhookEvent` type does not model. Do 2.4 first.

repo is the same seam a second production repo needs. Most of this phase is
threading a value through call sites that currently omit it.

## The blocking assumptions, ranked

1. **`worktreeDir` uses `path.dirname(repoPath)`** — `src/worker/worktree.ts:27-33`:
   `path.join(path.dirname(repoPath), \`wt-${cardId}\`)`. Two clones in one parent
   (`/home/pi/repos/a`, `/home/pi/repos/b`) both write worktrees into
   `/home/pi/repos/`. A card id appearing in two repos lands on the **same
   directory** — silent cross-repo corruption, the worst item on this list. Note the
   parent directory is *shared by design*: `test/worker/no-env.test.ts:123`
   pins "next to the repo, never inside it". Any fix must keep that.
   `plan/open-issues.md` "Notes / risks" already names this as a blocker for
   per-card concurrency.
2. **`reviews` PK is `(pr_number, head_sha)`** — `src/state/store.ts:124`. PR
   numbers are **per-repo**. Two repos both have a PR #7, and the same commit can
   legitimately appear in both (a vendored or cherry-picked tree). Today that is a
   cross-repo dedupe collision: repo B's review is silently refused because
   `startReview` found a posted row. **This is a live bug class, not a schema
   preference.**
3. **One memoized Octokit, one owner/repo, hardcoded base.** `src/github/client.ts:4-13`
   memoizes a single client from `config.github.token()`; all seven API methods
   read `config.github.owner()/repo()` (14 `config.github.*` reads across
   `client.ts` and `webhook.ts`, none anywhere else). `base: "main"` is hardcoded at
   `client.ts:94` and `REVIEW_BASE_REF = "origin/main"` at
   `src/reviewer/reviewer.ts:54` — a repo whose default branch is not `main` opens
   PRs against a branch that may not exist, and reviews a diff against nothing.
4. **`DiscordBot.send()` has no channel parameter.** `src/discord/bot.ts:180-186`
   sets `private channel` in the **constructor** from `config.discord.channelId()`,
   and `send(embed)` (`:243-247`) fetches that one channel. 12 call sites would all
   post into one channel: `src/worker/runner.ts:69,72,75,158,199,217,226,234,244`,
   `src/reviewer/reviewer.ts:157,492`, `src/github/webhook.ts:95`.
5. **Nothing persists which repo a card belongs to.** `jobs` has no repo column
   (`src/state/store.ts:74-84`, PK `card_id`); `agent_runs` and `reviews` likewise.
   After a restart — or a webhook delivery, which arrives with only a card id or a
   branch name — there is no answer to "which clone is this card's work in?"
6. **`TRELLO_BOARD_ID` is required and never read.** `src/config.ts:26` declares it
   with `req()`, and grep finds zero reads outside that definition (four tests
   `vi.stubEnv` it purely because the getter throws if absent). Trello is
   *identified* by three list ids — `READY_LIST_ID` (`trello/webhook.ts:30`),
   `REVIEW_LIST_ID` (`runner.ts:235`), `DONE_LIST_ID` (`github/webhook.ts:89`) —
   and no board anywhere. So the natural tenant key is configured but dead, and no
   inbound event is ever checked against a board.
7. **Neither webhook payload's repo/board discriminator is read.**
   `GitHubPRPayload` (`src/github/webhook.ts:12-21`) has no `repository`;
   `TrelloWebhookEvent` (`src/trello/webhook.ts:6-11`) has no `data.board`. Both
   fields are present in the real deliveries and cost nothing to use. Worse:
   `cardFromBranch` (`github/webhook.ts:52-55`) is repo-blind — `factory/abc` in
   repo B yields `"abc"` and, if repo A has a card `abc`, **repo A's job is marked
   done because repo B merged.** That is not a hypothetical; it is the current
   behaviour.
8. **One global worker gate and one global pause flag.**
   `src/worker/queue.ts:41` — `if (isPaused() || store.isRunning()) return;`, where
   `isRunning()` is `SELECT COUNT(*) FROM jobs WHERE status='running'` with no
   filter. One repo's stuck card freezes every repo. `/factory pause`
   (`src/discord/bot.ts:15-32`, a flag file at `data/paused`) pauses everything.
   This is open-issues #2's known global-gate problem, and multi-repo makes its
   blast radius N times worse.
9. **Container names collide on the card id.** `factory-${cardId}-orch`
   (`src/agents/graph.ts:247`), `factory-${cardId}-${runId}` (`spawn.ts:342`),
   `factory-review-${cardId}-${sha7}` (`reviewer.ts:347`). Docker names must be
   unique host-wide, so two repos running the same card id means the second
   `docker run` fails on a name conflict — and the timeout killer would target the
   wrong container. (Generic agent names `factory-agent-<pid>-<n>` at
   `container.ts:492-494` are already safe.)
10. **Deploy assumes one of everything.** One `factory.service`
    (`deploy/setup-factory.sh:153-192`), one `EnvironmentFile` (`:167`), one
    `REPO_PATH` (`:281`), one clone instruction (`:283`), one webhook pair
    (`:289-290`). The Caddyfile maps one host to one port (`:263-270`) — fine, since
    routing is already by path (`src/server.ts:29,40`).

## Shape of the change

### Tenants: a registry, not more env vars

Nine env vars per repo (`*_OWNER`, `*_REPO`, `*_PATH`, four list ids, channel id,
model, secret) does not scale as flat variables, and `.env` is already 90 lines of
comments.

**Recommendation:** one `FACTORY_REPOS_FILE` pointing at a JSON registry, with the
existing flat env vars kept as the single-tenant default so nothing breaks on
upgrade:

```jsonc
// /etc/factory/repos.json  (0600, root-owned — it holds per-repo tokens)
{
  "defaults": { "defaultBranch": "main" },
  "repos": [
    {
      "id": "widgets",                       // tenant key: in paths, container names, DB
      "repoPath": "/home/pi/repos/widgets",
      "github": { "owner": "acme", "repo": "widgets", "token": "…", "webhookSecret": "…" },
      "trello": { "boardId": "…", "readyListId": "…", "reviewListId": "…", "doneListId": "…" },
      "discord": { "channelId": "…" },
      "defaultBranch": "main",
      "model": "…", "reviewerModel": "…"     // optional overrides
    },
    { "id": "api", "...": "…" }
  ]
}
```

New `src/tenants.ts` — pure data + validation at boot, no I/O at call time:

- `repos(): RepoConfig[]`, `byId(id)`, `byBoard(boardId)`, `byGithubRepo(fullName)`.
- `byCard(cardId)` — answered by the **store**, not the registry (see below).
- **Boot-time validation that fails loudly**, in the spirit of #4's
  "fail loudly rather than silently misbehave": duplicate `id`, duplicate
  `boardId`, two repos with the same `owner/repo`, a `repoPath` that is not a git
  clone, a `readyListId` reused across boards, an unreadable token. Refusing to
  start is much cheaper than discovering it at delivery time.
- Every getter in `src/config.ts:23-48` (`trello.*`, `github.*`,
  `discord.channelId`) becomes **a method on the repo object** instead. Keep the
  flat getters reading the first/default repo for one release, so
  `scripts/*.ts` and the existing tests keep working, and say which is
  deprecated.

### Store: one DB, one added column, one changed primary key

Single database file is the right call — it keeps `reapStale` one sweep,
`/factory status` one view, and `activeRuns()` trustworthy. Two changes:

- [ ] `jobs` gains `repo_id TEXT NOT NULL DEFAULT ''` via **`ADD_COLUMNS`**
      (`src/state/store.ts:156-164` — the mechanism open-issues #1 established, and
      mandatory: `CREATE TABLE IF NOT EXISTS` will not add a column to a live DB).
      Same for `agent_runs` and `reviews` (denormalised, so a run or review is
      attributable without a join, and so `/factory status` can group per repo).
      `enqueue(cardId, cardName)` → `enqueue(repoId, cardId, cardName)`.
- [ ] **`reviews` PK must become `(repo_id, pr_number, head_sha)`.** SQLite cannot
      alter a primary key, so this reuses the `rebuildRunKey` precedent
      (`src/state/store.ts:190-230`): create-in-new-shape, copy, drop, rename,
      inside one transaction, *after* `applyAddColumns` and *before* the indexes.
      `keyedOnRunIdAlone`'s equivalent is `keyedWithoutRepo` — detect the old shape
      from `PRAGMA table_info`/`index_list` rather than assuming.
      Note `jobs.card_id` can stay a bare PK: Trello card ids are globally unique,
      so a card cannot exist in two boards — one repo per card, and the DB says so.
      That is why this is one column plus one rebuild, not a schema redesign.
- [ ] Worker queries become per-repo: `isRunning(repoId?)`,
      `nextQueued(repoId?)`, `all(repoId?)`, `activeRuns(cardId?, repoId?)`.
      `countRuns`/`countReviews` budgets stay card-scoped — they are per-card
      limits and a card belongs to one repo.
- [ ] **A migration test that hand-builds the pre-2.5 `reviews` table** in the old
      shape and asserts a live DB with rows survives, exactly as
      `test/state/store-attempts.test.ts:266-290` does for #1. Do not fake the
      migration.

### Queue: one worker per repo

`startWorker` (`src/worker/queue.ts:36-50`) currently owns one `setInterval`.
Give each repo its own gate and its own pause flag, and keep the single-process
model:

- [ ] `reapOrphans` stays global (it is a boot sweep over the whole DB).
- [ ] One interval per repo, each with `isPaused(repoId) || store.isRunning(repoId)`
      → `nextQueued(repoId)` → `runCard(job.card_id, bot, repo)`. A hung card
      blocks its own repo only. `ORCHESTRATOR_TIMEOUT_MS` (open-issues #2's cap) is
      what makes the blockage finite; note in the code that this is the reason #2
      was capped rather than fixed properly.
- [ ] `isPaused`/`setPaused` take a directory or a per-repo flag file
      (`src/discord/bot.ts:15-32` — currently one global `data/paused`).
- [ ] Consider a **host-wide concurrency cap** on simultaneous `runCard`s
      (`MAX_CONCURRENT_REPOS`, default 1 to preserve today's cost ceiling). Two
      repos at once doubles peak container count and therefore peak spend, which is
      the thing `MAX_PARALLEL_AGENTS` was set to control. Do not let that change
      implicitly by adding a repo.

### runCard: thread the repo, do not re-derive it

`runCard(cardId, bot, deps)` (`src/worker/runner.ts:126`) gains a `repo` — passed
in by the queue, or resolved from `store.get(cardId).repo_id` when a webhook
started it. Then, in order:

- `trello.getCard(cardId)` (`:154`) — unchanged, one Trello account can read many
  boards; if you ever split accounts, the client needs per-repo credentials.
- `worktree.create(cardId, repo.repoPath)` (`:155`) and `worktree.remove(...)`
  (`:247`) — **pass the path that the seam already accepts.**
- `github.createPR(branch, title, body)` (`:212`) → the repo's own client.
- `github.waitForCI(branch)` (`:220`) → the repo's own client.
- `trello.moveCard(cardId, repo.trello.reviewListId)` (`:235`).
- `bot.send(embed, repo.discord.channelId)` (`:158,199,217,226,234,244`).

### Discord: channel per call

- [ ] `send(embed, channelId)` (`src/discord/bot.ts:243-247`); one `Client`, one
      bot token, N channels — nothing else about discord.js needs to change.
      Keep a `defaultChannelId` for messages with no tenant (boot failures,
      `/factory status` replies are ephemeral and already go to the interaction).
- [ ] Slash commands (`src/discord/bot.ts:187-213`): `/factory status` groups by
      repo and shows a per-repo line (it already prints per-card spend);
      `/factory pause [repo]`, `/factory resume [repo]`,
      `/factory retry <card>` — retry resolves the repo from the job row, and
      **refuses a card belonging to a repo it cannot find**, rather than defaulting.
- [ ] `buildStatusText` (`src/discord/bot.ts:76`) is pure and channel-agnostic
      already; give it the repo grouping.
- [ ] Embeds: nothing names a repo today, and once N boards share one bot that is
      ambiguous if anyone looks at the wrong channel. Add the repo to the embed
      footer or title — cheap, and the failure without it is a human reading
      repo A's progress and thinking it is repo B's.

### Webhooks: route on the field that is already in the payload

- **GitHub** (`src/github/webhook.ts`): add `repository: { full_name: string }` to
  `GitHubPRPayload` (`:12-21`), resolve `byGithubRepo(full_name)` **before**
  anything else, and answer `200 {ignored: "unknown repository"}` for a repo not in
  the registry. Verify the HMAC with **that repo's** `webhookSecret` (GitHub secrets
  are per-webhook, so per-repo is the natural granularity; keep a global fallback).
  Then keep the `store.get(cardId)` guard **and** check `job.repo_id === repo.id` —
  that single comparison closes the cross-repo "repo B's merge marks repo A's card
  done" hole in item 7 above. `cardFromBranch` does not change: the branch is
  already namespaced by the repo it lives in, which is why the job-row check plus
  the payload check is the right pair.
- **Trello**: `action.data.board.id` (which 2.4 makes available) → `byBoard()`.
  An unknown board is ignored, not enqueued. Then `READY_LIST_ID` is per repo, so
  `handleTrelloWebhook` gains a repo and compares against `repo.trello.readyListId`
  instead of `config.trello.readyListId()` (`src/trello/webhook.ts:30`).
  `store.enqueue(repo.id, cardId, cardName)`.
  **2.4 is a hard dependency here** — the current type has no board field and the
  payload shape is wrong, so board routing cannot land before the shape does.
- **Reviewer**: `reviewPr(cardId, pr, deps)` gains the repo it belongs to and must
  use the repo's client for `getPullRequest`/`postReview`/`postLineComment` and the
  repo's `repoPath` for the detached worktree. Its `reviews` de-duplication claim
  gains `repo_id` (item 2).
  `buildReviewPrompt` should state the repo's **default branch**, because
  `REVIEW_BASE_REF` (`reviewer.ts:54`) is a hardcoded string. `createReviewWorktree`
  already fetches `refs/pull/<n>/head`; the base ref for `changedFiles` is the thing
  that must come from the tenant.
- Do **not** put a repo/owner/PR on the IPC wire. The host binds the run to one
  repo and the container never names it (`src/agents/ipc.ts:32-45`). With N repos
  that invariant is the isolation boundary: a repo A orchestrator with a valid
  token still cannot spawn into repo B's clone, because the spawner it reaches was
  constructed with repo A's `baseDir`/`gitDir`. Keep it that way and add a test.

### Per-repo agent config

`AGENT_MODEL` / `ORCHESTRATOR_MODEL` / `REVIEWER_MODEL` / `MAX_PARALLEL_AGENTS` /
`MAX_AGENT_RUNS` are process-global `config.factory` getters (`src/config.ts:90-122`,
read at `spawn.ts:340`, `graph.ts:238`, `reviewer.ts:331`). Move them onto the repo
object with the env var as the default. Same for
`FACTORY_AGENT_MODELS_FILE`/`_SETTINGS_FILE` if a repo needs a different endpoint —
these are already per-`runAgentInContainer` options (`src/agent/container.ts:43-66`),
so threading is mechanical.

### Deploy

- [ ] **One process, N repos** is the recommendation: one systemd unit, one port,
      one webhook surface, one agent image, one IPC bind. Two units on one host
      would fight over `WEBHOOK_PORT` and double the container ceiling with no
      operator noticing. Say this explicitly in the README so nobody reaches for a
      second service.
- [ ] `deploy/setup-factory.sh`: accept `REPOS_FILE`, install it to
      `/etc/factory/repos.json` (0600 root:root, like `factory.env`), and change the
      closing instructions from one clone (`:283`) to N, each **ssh remote** — the
      credential check in `src/agent/container.ts` (`assertGitDirSafeToMount`)
      refuses a token-bearing remote per repo, and one poisoned clone now blocks
      only that repo.
- [ ] Keep `FACTORY_IPC_BIND`/`_ADD_HOST` host-level (they already are,
      `deploy/configure-env.sh:29-31`) and say why they are not per-repo.
- [ ] nftables: the allowlist is host-based and already covers GitHub/Trello/etc.
      It needs additions only for **GitHub Enterprise Server or a self-hosted git
      host** — worth a comment at `deploy/setup-factory.sh:204`, not a code
      change.
- [ ] Caddy: unchanged (path routing already exists), unless you want
      per-repo paths — you do not, because the payload carries the repo.

## Sequencing, and why this order

Each step is independently shippable and green on its own.

1. **`src/tenants.ts` + registry file + boot validation + tests.** No behaviour
   change: one repo from the flat env vars becomes one `RepoConfig`. Everything
   else is built on that type.
2. **`worktreeDir` per-repo layout.** Small, isolated, and it removes item 1 — the
   worst bug on the list — before anything else can lean on it. Add the
   two-clones-one-parent test that *fails* first.
3. **Store: `repo_id` on `jobs`/`agent_runs`/`reviews` + the `reviews` PK
   rebuild + migration test.** Still single-repo behaviour (`repo_id` = the default
   repo).
4. **`createGithubClient(repo)`** — replace the module singleton and the 14
   `config.github.*` reads with per-repo clients; kill both hardcoded base branches
   (`client.ts:94`, `reviewer.ts:54`).
5. **`bot.send(embed, channelId)`** + thread `repo` through `runCard`.
6. **Webhook routing** for both providers (unknown repo/board ignored; job-row
   `repo_id` must agree).
7. **Per-repo worker gate + per-repo pause + `MAX_CONCURRENT_REPOS`.**
8. **Container names, prompts, embeds, per-repo model config.**
9. **Deploy, README, `.env.example`.**

Steps 1–5 change no behaviour for a single-repo install. Step 6 is where a second
repo becomes usable. Steps 7–9 make it safe to actually add one.

## Decisions this plan cannot make for you

1. **Per-repo tokens, or one token for all repos?** Per-repo fine-grained PATs are
   the safer default (a leaked token reaches one repo) and the registry shape
   allows both. But per-repo secrets multiply the things that expire. A GitHub App
   installation is the real answer at N>3: one set of credentials, per-installation
   repo scoping, and no expiring PAT — at the cost of app + private-key setup.
2. **Per-repo `GITHUB_WEBHOOK_SECRET`?** Recommended: GitHub secrets are
   per-webhook anyway, so one global secret is already a simplification that will
   eventually force a wrong answer.
3. **Same Trello account for every board?** The client builds one credential pair
   (`src/trello/client.ts:6`), so per-repo Trello accounts are a bigger change than
   per-repo GitHub tokens. If the boards live in different workspaces, say so now.
4. **Shared Trello list names or per-board ids?** `READY_LIST_ID` etc. are already
   per-board ids, so per-board config is a natural fit — no change of concept, just
   N of them.
5. **`/factory status` scope** — one message with all repos, or per-repo output
   triggered from that repo's channel? Per-channel output is the more natural fit
   for "one channel per repo", but commands are global to the app, so either is
   buildable.
6. **Default `MAX_CONCURRENT_REPOS`.** 1 preserves today's peak spend exactly.
   Unbounded-per-repo (i.e. one card per repo at a time) is what "it just works"
   looks like but silently raises the ceiling to N × 4 containers.

## Definition of done

- [ ] Two repos, two boards, two channels, configured by editing only
      `/etc/factory/repos.json` + restarting — no code change adds a repo.
- [ ] A card on board B never touches repo A's clone, branch, PR, channel or job
      row, with a test that would fail if it did (the merge-crossing case above).
- [ ] A hung or paused repo neither blocks nor is blocked by another repo beyond
      `ORCHESTRATOR_TIMEOUT_MS`.

## Notes / risks

- **The two worktree/DB collisions are bugs today, not future work.** Items 1 and
  2 can bite the moment a second repo exists, and both are silent. If 2.5 slips,
  land steps 2 and 3 first anyway — they are prerequisites for even a pilot second
  repo.
- **Cost is not per-repo by default.** Every budget knob is card-scoped
  (`MAX_AGENT_RUNS`, `REVIEW_MAX_RUNS_PER_CARD`). N repos multiply spend without
  multiplying any guard. `plan/open-issues.md` #6's per-card money view is what
  makes this visible; per-repo totals are what 2.5 should add to it.
- **Secrets move to a second file.** `/etc/factory/repos.json` holds per-repo
  tokens, so it gets the same treatment as `factory.env`: 0600, root-owned, outside
  the repo tree, read by systemd before privileges drop. The agent-container env
  allowlist (`src/agent/env.ts`) must not grow to carry them.
- **The in-process model is the risk to revisit first.** A crash or an event-loop
  stall in repo A's card now affects all repos — which is already true of the
  global worker gate and the shared `data/paused` flag today. Fixing per-repo
  gating without isolating crashes reduces the frequency, not the blast radius.
- **A repo whose default branch is not `main` is currently broken in two places**
  (`client.ts:94`, `reviewer.ts:54`) even for a single repo. Worth fixing in step 4
  regardless of whether the second repo is on `master`.
- **`config.factory.repoPath()` is `req()` — it throws** (`src/config.ts:50`). Once
  the registry supplies paths, keep the flat variable optional for tenants that use
  the registry, or a registry-only install dies at the first default-arg call in
  `worktree.ts` with a message about a missing env var nobody configured.
