# Phase 2.3 — PR reviewer agent (comments on PRs after create/update)

**Goal:** when a factory PR is **created or updated**, a reviewer agent pulls it down,
reviews the diff in a disposable worktree (containerized per 2.1), and posts the
results **as PR comments** (summary + line-level comments) via the GitHub API.

**Trigger:** GitHub webhook `pull_request` event, actions `opened` + `synchronized`,
branch matching `factory/<card>`. (Today the webhook only handles `closed` + merged.)

## Flow

```
GitHub webhook (opened|synchronized, factory/* branch)
  → reviewPr(cardId, pr)                       [host, has GITHUB_TOKEN]
    → dedupe: skip if a review for this head SHA is already running/posted
    → detached worktree at the PR head SHA     (wt-review-<card>-<sha7>, no branch)
    → reviewer container (2.1 infra, role "reviewer"):
        read-only tools + web; prompt = "review diff main...HEAD"
        (worktree is checked out at head, so `git diff origin/main...HEAD` works)
    → structured output contract (reviewer must end with):
        ```review-json
        {"summary": "...", "comments": [{"path": "...", "line": 12, "body": "..."}]}
        ```
    → parse → Octokit pulls.createReview:
        event: COMMENT, body: summary, comments: line comments (≤ REVIEW_MAX_COMMENTS)
    → Discord: reviewPostedEmbed(card, prUrl, commentCount)
    → clean up review worktree
```

## Steps

- [x] **1. `src/github/webhook.ts`** — restructure into small handlers (testable):
  - `onPrMerged(payload)` — today's merge logic, extracted as-is.
  - `onPrOpenedOrSynced(payload)` — branch match `factory/(.+)` →
    `reviewPr(cardId, payload.pull_request)` (fire-and-forget with `.catch(log)`;
    webhook always answers 200 quickly).
  - Dispatcher on `action`: `closed` → merge path; `opened`/`synchronized` → review
    path; everything else → 200 ignored.
- [x] **2. `src/reviewer/reviewer.ts`** —
  `reviewPr(cardId: string, pr: { number, html_url, head: { ref, sha } })`:
  - dedupe check via store (`reviews` table) → skip if same `head_sha` already
    `posted` or `running`;
  - create **detached** review worktree at `head.sha` (reuse 2.0 worktree helpers,
    new `createReviewWorktree(cardId, sha)` — no branch, `worktree add --detach`);
  - run role `reviewer` via `runAgentInContainer` (registered in 2.2's role registry —
    or standalone `src/reviewer/prompt.ts` if 2.2 is skipped);
  - parse structured output; post review; store result; remove worktree (finally).
- [x] **3. `src/github/client.ts`** — add:
  - `getPullRequest(number)` (re-check `state` right before posting; skip if closed);
  - `postReview(number, { body, comments })` →
    `rest.pulls.createReview({ event: "COMMENT", body, comments: comments.map(c =>
    ({ path: c.path, line: c.line, side: "RIGHT", body: c.body })) })`.
- [x] **4. State** — `reviews` table: `(pr_number, card_id, head_sha, status
  [running|posted|skipped|failed], posted_at)`; store methods
  `activeReviewFor(sha)`, `markReview(...)`.
- [x] **5. Structured-output parser** — `src/reviewer/parse.ts` (pure):
  extracts the last `review-json` fenced block; validates shape; drops comments with
  missing path/body or non-integer line; caps at `REVIEW_MAX_COMMENTS`
  (default 20); returns `{ summary, comments }` or `{ summary: rawText, comments: [] }`
  on any parse failure (review is never lost).
- [x] **6. Discord + config** — `reviewPostedEmbed(cardName, prUrl, count)`;
  `REVIEW_MAX_COMMENTS`, optional `REVIEWER_MODEL`.
- [x] **7. Docs** — README: what the reviewer checks (correctness, tests,
  security/secret-leaks, style), and that it re-runs on every push (`synchronized`).

## Notes / risks

- **Line numbers:** the agent must reference lines in the **new** file version
  (`side: RIGHT`). Prompt states this explicitly; parser drops comments whose line
  is out of range of the file (verified against `git diff` during implementation).
- **Double-review cost:** every push re-runs the reviewer — acceptable for factory
  branches (few commits); budget guard via `REVIEWER_MODEL` if needed.
- Webhook redelivery can duplicate `opened` events → the sha-dedupe in the store is
  the idempotency guard, not webhook ordering.

## Status — implemented, with these deviations

All seven steps and the test list are done (616 unit tests pass, 3 docker-gated
skips; `src/reviewer/**` is held to 85% lines like `src/agent/**`), and the real
flow has been run: `scripts/review-smoke.ts` spent 238 s of a real 27B model inside
a real container and landed three findings on the planted bugs — SQL concatenation,
`i <= users.length`, and `rows[0]` returning `undefined` where the catch path
returns `null` — each at `side: RIGHT` and at the reviewed commit. What differs from
the plan above, and why:

1. **The reviewer posts through a `post_review` tool; there is no `review-json`
   contract.** Step 2's "structured output the host parses" was decided against
   before implementation: `GITHUB_TOKEN` cannot enter a container, so the host posts
   either way, and a parsed block makes every finding depend on the run finishing.
   A reviewer that times out having read the whole diff would have posted nothing.
   Each finding now crosses `src/agents/ipc.ts` (the same framing, token check and
   reply shape 2.2 shipped — not a second protocol) and reaches the PR the moment it
   is made.
2. **Step 5's `src/reviewer/parse.ts` does not exist.** Its job is split three
   ways, all of it still pure and tested: frame validation in
   `ipc.ts:parseReviewRequest` (body present and sized, `path`+`line` both or
   neither, line a positive *safe* integer — `1e99` is an integer in floating
   point), location validation in `reviewer.ts:locateFinding` (path must be in the
   diff, line must be inside the file's new version), and `clampReviewBody` for
   GitHub's 65536-char body limit. Every edge case the parser's test list named is
   covered; the refusals also reach the model as a reason it can act on, which a
   dropped comment never did.
3. **Reviews are not `agent_runs` rows.** `HANDOFF-2.3.md`'s seam table said to add
   a `review` role row the same way; that was wrong, and open-issues #1 is the
   reason. `countRuns(cardId, attempt)` *is* the `MAX_AGENT_RUNS` budget, so review
   rows there would let a branch pushed twelve times consume a coder's budget and
   starve the card of the runs it needs to do its work. `reviews` is its own table,
   keyed on `(pr_number, head_sha)` as a real primary key, with its own budget
   (`REVIEW_MAX_RUNS_PER_CARD`, default 5) and its own usage columns;
   `/factory status` prints review spend as a separate line, because the two numbers
   drive two different knobs.
4. **`activeReviewFor(sha)` became `startReview({prNumber, cardId, headSha,
   maxPerCard})`, and it is a claim rather than a query.** Step 2's "check, then
   run" cannot be correct here: the reviewer posts mid-run, so a duplicate that
   arrives while the first is still working would post the same finding twice before
   any check-after-the-fact could notice. The row is written — `running` — inside a
   transaction that also applies the budget, and it is the refusal. `markReview`
   survived as named.
5. **Line ranges are verified against `git show HEAD:<path>`, not against
   `git diff`.** Step's note said "verified against git diff during implementation".
   A diff hunk does not tell you the file's length, and `docs/extra.md`-style cases
   matter: a file the PR *deleted* is in the diff but has no new version for a
   `side: RIGHT` comment to attach to. `fileLineCount()` reads the blob at the
   reviewed commit, which is the same content the reviewer was reading.
6. **The PR state is re-read before the container starts, not only before
   posting.** Step 3 said "re-check `state` right before posting"; it now happens
   there *and* once up front, because a review costs a model run and a closed PR is
   not worth one. It is also checked on *every* post — a review takes minutes and the
   DoD says nothing posts to a closed PR, which includes the fallback summary.
7. **Draft PRs are not reviewed.** Not in the plan; `opened` fires for drafts, and a
   draft is an author stating the diff is unfinished.
8. **A detached worktree needed a new return type.** `Worktree.branch` is a required
   `string` and a detached checkout has no branch; a sentinel would have been a name
   `deleteBranch` could later act on. Hence `ReviewWorktree { dir, head }`, and
   `createReviewWorktree(cardId, prNumber, headSha)` fetching
   `refs/pull/<n>/head` when the commit is not already local.
9. **Prerequisite bug, found while reading the code: no production caller ever set
   `addHosts`,** so 2.2's spawn channel was unreachable on a Linux host whatever
   `FACTORY_IPC_BIND` said — `host.docker.internal` is a Docker Desktop name and
   Docker Engine does not define it at all. `FACTORY_IPC_ADD_HOST` now exists,
   `graph.ts` and the reviewer pass it, and `configure-env.sh` writes it beside the
   bind because they are one requirement stated in two places. This was open-issues
   #4's missing half; #4 claimed the bind was the whole fix.
10. **`factory-agent.Dockerfile` copies the whole `extensions/` directory.** Naming
    each file meant a third extension could exist, typecheck, and be silently absent
    from the image — the failure being a model that refuses to use a tool it was
    never given.
11. **`GITHUB_API_BASE_URL` exists so the smoke can verify posting without
    posting.** The plan's opt-in check wrote to a real test repository. Pointing the
    real Octokit client at a local recording sink proves the same payload shapes
    (`side`, `commit_id`, `path`, `line`) without putting a bot's findings into
    whoever's tracker to test a script.
12. **`result.ok` gates the fallback summary.** Without it, a failed container's
    text — which `runAgentInContainer` *leads* with the failure reason — would be
    posted to a pull request as a review. Found by the test that checks a failed run
    records nothing.
