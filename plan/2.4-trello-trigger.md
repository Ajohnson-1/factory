# Phase 2.4 — make the Trello trigger actually fire

**Goal:** a card moved to **Ready** starts work. Today it does not, for three
independent reasons, and the failure is silent: the request arrives, is parsed, is
answered `200 {"handled":false}`, and nothing is enqueued.

This is the only path into the queue. `store.enqueue` has exactly three call sites
in the whole repo — `src/trello/webhook.ts:34`, `requeueCard` in
`src/discord/bot.ts:160` (which needs an existing job row, so it cannot start the
first one), and `scripts/graph-smoke.ts:232` (a test). Fix this before anything
else: every other phase is unreachable without it.

Read `plan/HANDOFF-2.3.md`'s "The lesson of BUG-1" first. This is that same shape
again, and worth stating plainly because it explains why 618 tests are green over a
broken trigger:

> `test/trello/webhook.test.ts:17-25` builds its own payload —
> `{ model: "card", action: "updateCard", card: {…}, list: {…} }` — and casts it
> `as TrelloWebhookEvent`. The handler asserts against that shape and the tests
> pass. Nothing in this repo has ever seen a real Trello delivery.

**Evidence this was never verified:** `plan/2.0-testing.md:157-162` records that the
Trello *client* was corrected against Atlassian's docs (wrong REST paths, wrong
bodies). `plan/2.0-testing.md:86` then *specified* the inbound shape as "returns
false for wrong `model`, wrong `action`, card missing, list ≠ Ready" — i.e. the
tests encode the same invented flat shape the code has. The outbound half was
checked; the inbound half never was.

## The three blockers

Verified against https://developer.atlassian.com/cloud/trello/guides/rest-api/webhooks/

### 1. The payload shape is wrong

`src/trello/webhook.ts:6-11`:

```ts
export interface TrelloWebhookEvent {
  model: string;                                  // ← Trello sends an OBJECT
  action: string;                                 // ← Trello sends an OBJECT
  card?: { id: string; name: string; idList: string };   // ← not top-level
  list?: { id: string; name: string };                   // ← not top-level
}
```

`src/trello/webhook.ts:26-30` is the guard:

```ts
if (body.model !== "card" || body.action !== "updateCard" || !body.card) return false;
if (body.list?.id !== config.trello.readyListId()) return false;
```

Trello's own docs, "Example Webhook Response": *all webhooks contain these 3
fields* — `action` (an Action object with `id`, `type`, `data`, `memberCreator`),
`model` (the watched object — a board, card, list), and `webhook`. The action's
type is `action.type`, and the card is `action.data.card.id`.

So for every real delivery `body.model` is an object, `body.model !== "card"` is
true, and the handler returns `false` at line 24. Not intermittently. Always.

### 2. The webhook cannot be created in the first place

From the same page: *"We run a quick HTTP HEAD request on the URL, and if a 200
status code is not returned in the response, then the webhook will not be
created."*

`src/server.ts:23-43` routes exactly three things — `GET /health`,
`POST /webhook/trello`, `POST /webhook/github` — and everything else falls to
`json(res, 404, …)` at `:43`. A `HEAD /webhook/trello` gets 404, so `POST
/1/webhooks` fails. There is no HEAD branch anywhere: repo-wide grep for `HEAD`
returns only git-HEAD references and `JSON_HEADERS`.

Also worth killing in the docs: `README.md:33-35` tells the operator to add a
webhook from the **card menu**, per card. Trello's docs say webhooks are "only
accessible through the API currently" — there is no UI — and a per-card `idModel`
would mean one webhook registration per card forever. A **board-level** webhook is
the right scope and is confirmed by the docs' own action table: `updateCard` fires
for Card, List, **Board** and Member.

### 3. The one auth mechanism on that route is unusable

`src/trello/webhook.ts:47-51`:

```ts
export function checkSecret(req: IncomingMessage): boolean {
  const secret = config.factory.webhookSecret;   // WEBHOOK_SECRET
  if (!secret) return true;                       // ← unset ⇒ open endpoint
  return req.headers["x-webhook-secret"] === secret;
}
```

Trello cannot set custom headers. So `WEBHOOK_SECRET` set ⇒ every delivery is
401'd; `WEBHOOK_SECRET` unset ⇒ the route is unauthenticated and anyone who can
reach it can enqueue arbitrary card ids and start paid model runs. It is one state
or the other, and neither is right. Trello's real mechanism is an
`X-Trello-Webhook` header: base64 HMAC-SHA1 over the body plus the callbackURL,
keyed with the app secret from https://trello.com/apps/admin.

Note this is a different problem from `GITHUB_WEBHOOK_SECRET`, which does work
(`src/github/webhook.ts:29-42`, HMAC-SHA256 over the raw body with
`timingSafeEqual`). The GitHub path is fine. The Trello path is not.

## Two ways out, and which one I would take

Both fix blocker 1. They differ on whether you keep a public inbound endpoint that
you cannot authenticate.

### Option A — polling (recommended)

Every tick, ask Trello which cards are in each board's Ready list, and enqueue
whatever is not already known.

Why this is the better trade here, concretely:

- **It deletes blockers 2 and 3 instead of fixing them.** No HEAD probe, no public
  `/webhook/trello` route, no signature scheme, no app secret to custody. The
  factory stops needing an inbound path from Trello at all — only GitHub keeps one,
  and GitHub's HMAC already works.
- **`jobs` is already the seen-set.** No new table, no dedupe state. Enqueue when a
  Ready card has no job row, and when its row is terminal — which is precisely
  `Store.enqueue`'s existing contract (`src/state/store.ts:273-303`): `queued`/
  `running` return `{queued:false}`, a terminal status bumps `generation` for a
  fresh attempt. A card dragged out of Ready and back re-triggers; a card being
  worked does not double-trigger. The open-issues #1 work is what makes this safe.
- **It survives Trello's webhook lifecycle.** Per the docs: three retries at
  30/60/120 s, then a webhook is disabled after 30 days and 1000+ consecutive
  failures, and a `410 Gone` answer deletes it outright. A restart that leaves the
  port down for a weekend silently kills the trigger and nobody notices until a
  card sits in Ready for a week. A poll cannot desynchronise like that.
- **It fits the shape that already exists.** `startWorker`
  (`src/worker/queue.ts:36-50`) is a 15-second `setInterval` that already gates on
  `isPaused()` and `store.isRunning()`. Polling is one more step in that loop, not
  a new subsystem.
- Latency is the cost: up to one tick (15 s) instead of instant. For a factory where
  a card then spends minutes in a container, that is not the number anyone cares
  about.

Costs to confirm rather than assume: Trello rate-limits per key *and* per token
(the docs do not state the numbers on the webhooks page). One request per board per
tick is small, but verify the limits page before adding boards, and back off on
`429` rather than retrying blindly.

### Option B — keep webhooks, do them properly

If you want sub-second pickup. Required work beyond fixing the shape:

- Answer `HEAD` with `200` on `/webhook/trello` (and only there) so webhook
  creation succeeds; consider `410` on a path you no longer serve so stale
  webhooks clean themselves up.
- Verify `X-Trello-Webhook` = base64 HMAC-SHA1(`appSecret`) over
  **`JSON.stringify(body) + callbackURL`**, and add `TRELLO_APP_SECRET`. Do this
  with the raw bytes and the parsed body both considered: Trello's own sample
  hashes the *re-serialized* body (`JSON.stringify(request.body)`), so raw-vs-parsed
  is a live question that must be settled against a real capture, not by
  reasoning. The comparison must be constant-time, like `verifySignature`.
- Register one webhook per board (`idModel` = board id) via
  `trello.createWebhook(boardId, url)` — note the current signature
  (`src/trello/client.ts:53-67`) names its first parameter `cardId`, which is a
  misnomer once the model is a board, and it has **no production caller at all**
  today.
- Persist webhook ids so a redeploy does not stack registrations, and be aware
  webhooks belong to the token that created them: if `TRELLO_TOKEN` is rotated or
  revoked, Trello deletes them silently.
- Keep it fire-and-forget and always answer 200 fast, like
  `src/github/webhook.ts` now does for the same reason (a miss gets redelivered,
  and redelivery of a `move to Ready` is a duplicate run attempt).

### Either way, these three things must change

1. **Capture one real delivery before writing the parser.** Add a debug mode that
   logs the raw body of `POST /webhook/trello` to a file (never to Discord, and not
   at `info` — it can contain card content). The docs are authoritative on
   `action.type` and on `action.data.card.id`; they are *not* explicit on which
   field carries the destination list for a card move. `listAfter` / `listBefore`
   under `action.data` is the expected shape and is what `updateCard` is documented
   to carry, but do not code it from memory.
   Preferably make the decision not matter: see the next point.
2. **Do not trust the payload for the destination list.** When a delivery says a
   card moved, call `trello.getCard(cardId)` and compare `card.idList` to
   `READY_LIST_ID`. `getCard` already exists (`src/trello/client.ts:30-32`),
   `runCard` already calls it at `src/worker/runner.ts:154`, and `TrelloCard.idList`
   is already typed at `src/trello/client.ts:21-29`. This makes the trigger correct
   under either payload shape and immune to a Trello format change — at the cost of
   one API call per candidate event, which is bounded by the tick, not by traffic.
3. **Stop discarding the verdict.** `src/trello/webhook.ts:34` throws away
   `store.enqueue`'s `{queued, requeued, generation}`; already logged as a known
   hole at `plan/open-issues.md` §"Status". Log which case happened, because
   "refused, a card is already running" is exactly the message an operator needs and
   is currently indistinguishable from "nothing arrived".

## Steps — Option A (recommended)

- [ ] **0. Capture, then decide.** Ship the raw-body-to-file debug path, get one
      real `updateCard` from a Ready move, paste it into this plan under a
      "Captured payload" heading. Every later step is cheap; guessing wrong here is
      the bug you are fixing. *(Gate: this is done before the parser is written, not
      after.)*
- [ ] **1. `src/trello/client.ts` — `listCards(listId)`.**
      `GET /1/lists/{id}/cards` returning `{id, name}[]`. Needs a new typed
      response; keep `seg()` on the id and keep `api()`'s existing key/token
      query-string construction (`src/trello/client.ts:6`) untouched.
- [ ] **2. `src/trello/poller.ts` (new) — `syncReadyList(deps)`.** Pure-ish,
      injectable `{store, trello, readyListId}`, returning the ids it enqueued and
      the verdicts for the ones it did not. One call per board. No knowledge of
      HTTP. Handle a `getCard`/`listCards` failure by logging and skipping the tick
      — a Trello outage must not mark anything failed.
- [ ] **3. Decide-on-reconcile: `enqueue`, never `re-enqueue`.** Call
      `store.enqueue(id, name)` and log its verdict
      (`queued` / `requeued +N` / `refused: already running`). A card that fails
      while still sitting in Ready must be retryable, and the terminal-status rule
      in `Store.enqueue` already gives you that — do not add a seen-set that
      suppresses it.
- [ ] **4. Wire it into the tick — `src/worker/queue.ts:39-48`.** Poll *before*
      the `store.isRunning()` gate returns early, or the queue stops feeding itself
      whenever a card is in flight. This is the one ordering trap in the change;
      there is a test for it below.
- [ ] **5. `TRELLO_POLL_MS`** in `src/config.ts` (a `num()` getter alongside the
      others at `src/config.ts:50+`, default 15000, 0 disables) and `.env.example`.
      Document the rate-limit caveat and the backoff requirement.
- [ ] **6. Kill the dead inbound route, or keep it honest.** If nothing registers a
      webhook any more, delete `POST /webhook/trello`, `checkSecret`, and
      `WEBHOOK_SECRET` — and update the secret-isolation table at `README.md:59-63`
      which currently lists `WEBHOOK_SECRET` as a credential the agents must not
      see. Leaving an unauthenticated enqueue endpoint reachable behind Caddy, with
      no code that uses it legitimately, is the worst outcome of the three. If you
      also do Option B, keep the route and implement its signature verification in
      the same commit.
- [ ] **7. Docs.** Replace `README.md:33-35` (the card-menu instruction that does
      not exist) and `deploy/setup-factory.sh:289-290`'s "Trello card webhook" line
      with the polling reality: a Ready list id is all Trello needs now, and no
      inbound Trello traffic is expected.
- [ ] **8. Note the interaction with 2.5.** The poller takes one ready-list id
      today; multi-repo makes it one per board. Design `syncReadyList` to accept
      the list id as a parameter rather than reading config internally, so 2.5 is a
      loop and not a rewrite.

## Steps — Option B only, on top

      service — a service that creates remote state on boot is a redeploy hazard.
      Rename the parameter from `cardId` to `idModel` while there.

## Unit tests

Everything below is written against a **recorded** payload (step 0), pasted into
the fixture as JSON. That is the entire point: the current fixture
(`test/trello/webhook.test.ts:17-25`) was authored from the code's assumptions and
is what let the bug through.

- [ ] `test/trello/poller.test.ts` — fake `trello` client, real `createStore`
      against a temp file (house style, cf. `test/state/store-attempts.test.ts`):
      - a card in Ready with no job row → enqueued, verdict `queued`;
      - the same card on the next tick → not enqueued again, one `queued` row;
      - a card whose job is `done`/`failed` and is back in Ready → requeued,
        `generation` bumped, and the attempt budget resets with it (ties to
        open-issues #1's test at `test/agents/spawn.test.ts:282`);
      - a card whose job is `running` → refused, and the refusal is *logged*;
      - `listCards` throws → no jobs touched, no crash, next tick still runs;
      - two boards' list ids → each poll only enqueues its own (the 2.5 seam).
- [ ] `test/trello/webhook.test.ts` — **replace** the fixture with the captured
      payload; delete `readyMove`'s invented shape and add a comment naming where
      the JSON came from, the way `test/agents/spawn.test.ts:11-30` documents
      BUG-1's fake. Keep the "not a card update" and "wrong list" cases; add
      "a non-`updateCard` action type is ignored" and "a comment added to a card in
      Ready does not re-enqueue it".
- [ ] `test/server.test.ts` — for Option B: `fetch(base, {method:"HEAD"})` on
      `/webhook/trello` answers 200 with no body, and HEAD on an unknown path is
      still 404. This file already boots a real server and fetches it
      (`test/server.test.ts:21-24`), so no new harness. For Option A: the route is
      gone, and the existing 404 test is extended to cover it.
- [ ] `test/worker/queue.test.ts` — **the ordering test.** With
      `store.isRunning()` false→never and a card pending, a tick must still poll.
      Concretely: while a card is running, the poller still runs, and a Ready card
      is enqueued even though nothing is being dispatched. This is the failure mode
      a reviewer of the diff would otherwise miss, because both orders pass every
      other test.
- [ ] `test/trello/client.test.ts` — `listCards` hits `/1/lists/{id}/cards`,
      url-encodes the id, and carries `key`/`token` exactly as the other methods
      do. `createWebhook`'s test at `:113-125` pins `idModel`; update it when the
      parameter is renamed.
- [ ] `test/config.test.ts` — `TRELLO_POLL_MS` default, override, and `0`
      meaning off. If `WEBHOOK_SECRET` is removed, delete its assertions
      (`test/config.test.ts` currently stubs it).

## Definition of done

- [ ] **A card dragged to Ready in the Trello UI starts a job on a real board, on
      a real deploy, with no manual SQL and no code invocation.** Until this is
      observed once, nothing above counts — it is the exact step every prior phase
      skipped by trusting the fixture.
- [ ] The captured payload is pasted into this file, so the next session does not
      re-derive it.
- [ ] The old invented-shape fixture is gone, not kept "for coverage". A fake that
      models a request the provider cannot send is not coverage; it is the bug's
      alibi.
- [ ] `store.enqueue`'s verdict is logged in every case, and a duplicate is
      visibly refused rather than silently dropped.
- [ ] No unauthenticated route can enqueue work: either the Trello POST endpoint
      verifies `X-Trello-Webhook`, or it does not exist.
- [ ] `npm test` green, hermetic (no network), and the tick-ordering test fails
      against a poll-placed-after-the-gate implementation.

## Notes / risks

- **This is a defect fix, not a feature.** No new subsystem. If the diff grows a
  queue, a scheduler, or a state machine, it has drifted.
- **A poll that trusts its own last answer** is the failure mode to avoid: poll
  Trello, don't cache "cards I have seen" in memory, because a restart must not
  re-enqueue the board or forget a card that is legitimately waiting. `jobs` is the
  only durable memory here, deliberately.
- **Do not mark a card failed because Trello answered slowly.** A `getCard` or
  `listCards` timeout skips the tick. Today `runCard` calls `trello.getCard` at
  `src/worker/runner.ts:154` with no try/catch of its own — it relies on the
  surrounding `catch` at `:241`, which marks the job failed. That is defensible for
  a run already in progress; for a poll it is not, because the card has done nothing
  wrong yet.
- **`TRELLO_BOARD_ID` (`src/config.ts:26`) is required and read zero times**
  outside its own definition — confirmed by grep across `src/`, `test/`, `scripts/`
  and `plan/`. Option A can finally use it, or it should be dropped rather than
  left as a required var that throws for nothing.
- **Ordering: 2.4 before 2.5.** `plan/2.5-multi-repo.md` routes a board to a repo,
  and both trigger paths (poll and webhook) need the same corrected payload and the
  same `getCard`-based verification. Doing it twice is how the second copy ends up
  subtly wrong.
