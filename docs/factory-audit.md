## What the factory is today

The factory is a looping card pipeline over a Trello board where **the board is the state machine and the comments are the audit log**: lists `Ready → Plan → Implement → Review → QA → Deploy → Verify → Done` are stage state (only the scheduler moves cards), and every stage posts exactly one first-token-tagged comment (`[PLAN]`, `[IMPL]`, `[REVIEW:APPROVE|CHANGES]`, `[QA:PASS|FAIL]`, `[DEPLOY]`, `[VERIFY:PASS|FAIL]`, `[ASK]`, `[HUMAN]`, `[RESUME]`, `[DAEMON-CRASH]`) — `docs/factory.md`, "Board contract". Each card runs in an isolated git worktree with a `factory/<id>` branch cut from `origin/master`, concurrency-capped at 3 (`docs/factory.md`, "Isolation — one worktree per card"). A hard merge gate (rebase onto `origin/master` + `node scripts/factory.js mergeable`) precedes Review, and merges are always `--ff-only` into `master` followed by an `npm test` integration check (same section). `scripts/factory-daemon.js` removes the manual trigger: it polls Ready, moves Ready → Plan itself before spawning a headless run (`dispatch`, `planDispatch`), supervises crash retries via `[DAEMON-CRASH]` comments whose counts are read back from the card (`handleCrash`, `MAX_CRASH_RETRIES`), applies per-run caps through `agentArgs` (`--max-time` 2 h, `--max-cost` $10, optional `--model`), and survives self-restart via a detached bootstrap guard ("Auto-start daemon" in `docs/factory.md`). Blocked agents contact humans through the ask protocol (`scripts/lib/factory-ask.js`: post `[ASK]` → Discord DM → block until a human comment answers, exit 1 on timeout), and a supervised comment-resume watcher (`scripts/lib/factory-comment-resume.js`) picks cards back up at their **current** stage when a human comments on an in-flight card, including the stuck-Verify trap. Done arrivals ping the owner over one dedup state file ("Pinging on Done"). Post-merge, the scheduler deploys via `scripts/deploy.js` (build/deploy over SSH, `.deploy-history`; a `rollback` command exists — `deploy.js` lines ~24–26 and ~327–342) and gates on `scripts/verify-deploy.js`, whose stdout is a machine-verdict JSON that gets embedded in the `[VERIFY:FAIL]` comment on failure. `scripts/prod-watch.js` probes prod every 300 s, detects DHCP drift, and **opens a `[PROD-WATCH]` investigation card in Ready on an outage**, so the factory investigates its own production.

## Section C — Prioritized improvement list

Actionable prose only (no code), per the card. Every item traces to a factor or blog theme above and to a current-factory evidence pointer.

### High

- **C-H1 — Require evidence of verification on every `[IMPL]` comment** (Blog theme B1; factor 3). *Why:* the blog's strongest claim — giving the agent a way to verify its work and making it show the output is the highest-leverage habit for agent-authored code. *Gap:* "self-run focused tests" is intent in the Stages table; nothing in the `[IMPL]` contract (docs/factory.md "Stages", "Board contract") obliges the implementer to record which checks ran and what they printed, so the reviewer and QA inherit an unverified claim. *Improvement:* extend the `[IMPL]` comment convention so it must include, in prose, the exact commands or checks run and their observed results (test counts, exit codes, a screenshot path for UI work), plus a short note of what the checks would miss. The reviewer treats missing evidence as an automatic `[REVIEW:CHANGES]` finding — cheap, and it converts the whole downstream pipeline from trust-based to evidence-based.
- **C-H2 — Verify reviewer findings with a second pass before they burn a bounce** (Blog theme B4; factors 8, 10). *Why:* the blog only posts findings that several verifying agents agree are real, drops style-only findings, and tags severity — because false positives cost the most when the fixer is an agent. *Gap:* a single reviewer's `[REVIEW:CHANGES]` (`docs/factory.md` "Stages") is authoritative, and in the factory each false-positive finding costs an entire Implement re-run against the 3-bounce cap (`needs-human` at 3 — "Scheduler loop"). *Improvement:* between Review and bounce, add a short verification sub-step (a fresh-context second agent per finding: real, style-only, or pre-existing) so only confirmed findings drive the bounce; carry an Important/Nit/Pre-existing tag in the finding list so Nits never consume a bounce and pre-existing issues are logged without blocking.
- **C-H3 — Add a blocking security-review layer to the pipeline** (Blog theme B6). *Why:* the blog runs security review as its own automated, blocking layer; nothing merges with an open security finding. *Gap:* the Stages table has no security step at all and `scripts/verify-deploy.js` only checks runtime health, so a card touching auth, tokens, or the Trello/Discord credential plumbing (`docs/factory.md` "Credentials") gets exactly the generic review. *Improvement:* add a security-focused agent stage (or a mandatory Review sub-pass) with its own tagged verdict, seeded from a short list of what matters in this repo (secrets handling, inbound input from Discord/Trello, SSH/deploy paths); block progression to QA while security findings stay open.
- **C-H4 — Risk-tiered human approval before Deploy, set by the change** (Blog themes B8 and B15; factor 7 mechanism exists to carry it). *Why:* today the factory merges and deploys with zero humans ("Scheduler loop": QA:PASS → merge → Deploy), and the blog's guardrail is that the *change*, not the author, decides where a person must look. *Gap:* no tier logic anywhere in `scripts/factory-daemon.js` or the board contract; a diff touching `scripts/deploy.js`, `config/`, or CI-adjacent files auto-merges like a docs fix; bot verdicts (`[QA:PASS]`) already act as de-facto approvals, which the blog explicitly forbids. *Improvement:* classify each card's risk from its diff (paths touched, lines, whether it can reach credentials or prod deploy), then require an explicit `[HUMAN]` approval comment — keyed to the exact sha that passed QA — before the Deploy move for medium/high tiers, while docs-only and additive cards keep the current zero-human path. Always-human the deploy scripts, config, and credentials paths. The ask protocol (`scripts/lib/factory-ask.js`) already provides the notify-and-wait machinery.
- **C-H5 — Wire rollback into the failure path and adopt a which-layer-failed incident review** (Blog themes B10 and B17; factors 5, 8). *Why:* the blog's last layer is fast rollback plus asking which layer let a problem through; the factory detects fast but only fixes forward. *Gap:* `[VERIFY:FAIL]` bounces to Implement ("Stages") while prod serves the failed build, even though `scripts/deploy.js` already implements history-based `rollback` (its own usage text and history entry logic) that no pipeline step calls. *Improvement:* make the scheduler run the existing rollback on `[VERIFY:FAIL]` (restoring the last known-good image, recording a tagged `[ROLLBACK]` comment for the audit log) before starting the fix-forward bounce; when an outage or bad deploy is closed (`[PROD-WATCH]` cards — `scripts/prod-watch.js`), have the closing comment answer "which layer should have caught this" so the answer can later seed the eval set (C-M11).

### Medium

- **C-H6 / C-M13 — Measure the pipeline and the reviewer** (Blog themes B12, B17, B18; factors 5, 8). *Why:* the blog's whole optimization is optimizing human time with revert/incident rates as the guardrail, and measuring review noise by how people respond to findings. *Gap:* nothing computes anything — bounce rates, crash rates, ask latency, per-card wait time, cost against the $10 cap (`agentArgs` in `scripts/factory-daemon.js`), and finding disposition are all implicit in comments and logs (`data/factory-daemon/<card>.log`) but never aggregated. *Improvement:* a periodic reporting pass that reads the board (the state model makes this cheap — every signal is already a comment per factor 5) and emits a report card: bounces per card, time per stage, crashes, `[ASK]` latency, fraction of `[REVIEW:CHANGES]` findings actually fixed vs dismissed, plus prod-down count from `data/prod-watch.json` as the guardrail. Start with a scheduled card that does the counting and posts the summary.
- **C-M2 — Promote per-stage prompts to owned, versioned artifacts** (Factor 2). *Why:* the factor demands prompts be first-class code — owned, diffable, testable; the blog feeds every reviewer miss back into an instruction file. *Gap:* the only repo-owned prompt is `buildRunPrompt` (`scripts/factory-daemon.js` ~line 95); planner/implementer/reviewer/qa role prompts (`docs/factory.md` "Stages") live inside the omp harness, invisible to git, and `FACTORY_MODEL` swaps change behavior with nothing versioned to re-score. *Improvement:* move each stage's role/verdict instructions into repo-owned stage prompt documents that the scheduler prompt quotes or points the subagent at, so prompt changes get reviewed, committed, and — with C-M11 — scored like code.
- **C-M3 — Curate per-stage context instead of replaying the raw comment trail** (Factor 3). *Why:* the factor's core claim is that building the context deliberately (what to include, what to drop, resolved errors hidden) is where quality comes from. *Gap:* every stage re-reads the card's full raw trail via `factory.js read` ("Board contract"), so on bounced cards stale verdicts, crash notices, and embedded verify JSON compete with the live requirements. The resume watcher shows curation is possible: it quotes only the triggering comment ("Listening for human comments"). *Improvement:* define, per stage, what context that stage needs — Implement: description + plan + latest findings only; Review: diff + description; QA: acceptance criteria — and have the scheduler prompt state that filter, or pre-summarize old verdicts into one short digest comment after each bounce so the raw trail stays audit-only.
- **C-M4 — Compact crash errors onto the card for the retrying run** (Factor 9). *Why:* self-healing requires the error to be in the retrying model's context window. *Gap:* `handleCrash` (`scripts/factory-daemon.js`) posts only `run exited <code>` while the actual failure text stays in `data/factory-daemon/<card>.log` ("Auto-start daemon"), so the re-queued run restarts at Plan knowing only an exit number. *Improvement:* when a run crashes, include a short tail of the run log (last error lines, trimmed to comment size) inside the `[DAEMON-CRASH]` comment, so the next run's `factory.js read` sees the failure content in context and can avoid repeating it; the `[VERIFY:FAIL]`-embeds-JSON pattern (Stages table) is the precedent.
- **C-M5 — Make crash recovery stage-aware so committed work is never redone** (Factor 12). *Why:* a stateless reducer resumes deterministically from the log; the factory's plain crash path restarts the fold. *Gap:* the docs themselves flag the flaw — re-queuing "would restart it at Plan and redo committed work" ("Auto-start daemon"), which is why resume runs get the no-re-queue exception in `handleCrash`, but ordinary crashed runs still re-queue to Ready. The worktree/branch is mutable state outside the event log. *Improvement:* route crashed runs through the same stage-aware resume machinery the comment watcher uses (spawn at the card's current list with the reuse-the-worktree instruction) instead of Ready→Plan, reserving the full re-run for crashes that happen before the first stage comment exists.
- **C-M6 — Add per-area review ground-truth files** (Blog theme B2). *Why:* the blog's reviewers follow owner-written per-area docs stating what failure looks like, capped nits, skip paths, and file:line evidence — and compliance with them is itself checked. *Gap:* `AGENTS.md` (26 lines) covers repo rules and `docs/factory.md` covers process, but no area doc tells the reviewer what matters in the bot's memory/embedding code, the deploy/SSH surface, or the Trello/Discord I/O; the reviewer prompt demands none of it. *Improvement:* add short per-area review guidance documents (a couple of sentences each: failure mode, must-check behaviors, paths to skip, evidence format) and point the Review stage prompt at them; periodically spot-check that reviewer findings actually follow them.
- **C-M7 — Scale review depth with risk and widen the review brief** (Blog theme B3; factors 3, 10). *Why:* the blog matches effort to stakes — Deep review only where a missed bug is expensive — and reviews the diff against the whole repo plus stated intent. *Gap:* the Review row is uniformly "diff + mergeable" (Stages table) regardless of card risk; whole-repo fit and "does this solve its stated problem" are not part of the documented review brief. *Improvement:* tie review depth to the same risk classification as C-H4 (quick pass for docs/additive cards; full pass reading surrounding modules and the card's intent for high-risk ones) and state the intent-check question in the reviewer brief.
- **C-M8 — Require a per-finding response on bounce** (Blog theme B5). *Why:* "every finding has to be answered — fix it or resolve with a reason" is what makes convergence auditable. *Gap:* nothing obliges a bounced Implement to address each `[REVIEW:CHANGES]` item; unresolved findings reappear silently next pass. *Improvement:* make the bounce contract require the next `[IMPL]` comment to enumerate the prior findings with disposition (fixed — where, or not-a-bug — why), and let the reviewer's next pass check that enumeration before judging the diff.
- **C-M9 — Make blocking checks independent and capture a test/risk/revert note** (Blog theme B7). *Why:* the blog gates on dozens of automated checks no human (or author agent) can waive, plus a template recording how it was tested, the risk, and how to undo. *Gap:* `npm test`/lint run inside agent sessions (Stages table; post-merge check in "Isolation") — enforcement is agent discipline, not an independent gate — and no structured testing/risk/revert record exists on the card. *Improvement:* have the deterministic scheduler (daemon), not the QA agent, run the blocking check suite against the worktree tip and treat a non-zero exit exactly like `[VERIFY:FAIL]` (bounce, counted); require `[IMPL]` to carry how-tested / risk / how-to-revert prose, mirroring the blog's PR template.
- **C-M10 — Close the merge race and start gradual rollout** (Blog theme B9). *Why:* the blog's merge queue re-runs everything against fresh main so two separately-green changes cannot combine into a broken main; then flags/internal-first limit blast radius. *Gap:* the merge gate rebases onto a fetched `origin/master` at gate time ("Scheduler loop" MERGE GATE) but with 3 cards in flight (`FACTORY_MAX_PARALLEL`) the first push can invalidate the second's tested base before its `--ff-only` merge, and there is no flag/staged-release machinery — deploy is one-shot to the single prod host (deploy row). *Improvement:* re-check that `master` has not advanced (or re-run the gate) immediately before each `--ff-only` merge, re-testing if it has; then take the cheap first step of internal-first: use the existing prod watchdog window as the canary interval before considering more cards in flight.
- **C-M11 — Build an incident/eval set and score every reviewer/prompt/model change against it** (Blog theme B11; factor 2). *Why:* the blog's improvement loop only keeps a reviewer change if its score on expert-checked past incidents goes up. *Gap:* `buildRunPrompt` edits, `FACTORY_MODEL` changes (`agentArgs`), and omp harness upgrades currently land blind — the lib unit tests (`tests/factoryDaemon.test.js` etc.) cover plumbing, not judgment. *Improvement:* harvest past `[REVIEW:CHANGES]`/`[QA:FAIL]`/`[VERIFY:FAIL]`/incident cards into a curated set of cases with the confirmed answer, and before keeping a prompt/model change, replay the Reviewer role over the set and compare; each C-H5 incident review feeds a new case.

### Low

- **C-L1 — Nightly standing review sweep over merged code** (Blog theme B14). *Why:* the blog runs review agents nightly over existing code to catch old bugs before they resurface. *Gap:* the factory is purely reactive — the daemon only dispatches Ready arrivals ("Auto-start daemon"). *Improvement:* a nightly scheduled card (cron → `factory.js add`) whose agent reviews a slice of recently merged code against the review ground-truth docs and files findings as follow-up Ready cards — reusing the existing pipeline instead of new machinery.
- **C-L2 — Generate on-demand codebase explainers** (Blog theme B16). *Why:* the blog's answer to "if machines read everything, how does anyone learn the code?" is asking for an explainer of exactly the slice you need instead of reading trivial diffs. *Gap:* the audit trail (raw comment streams on closed cards) is the only institutional record; nothing distills understanding. *Improvement:* when a human wants to learn an area, run a one-off explainer through the same headless-run machinery and commit the result under docs — the pipeline already proves it can produce and merge docs-only cards (like this audit).
- **C-L3 — Move factory notifications from private DMs to an open channel** (Blog theme B17). *Why:* the blog credits open channels with letting anyone see what is being built and point an agent at a gap — quality maintained without a gate on every line. *Gap:* ask pings and Done pings DM the owner one-to-one ("Asking a human", "Pinging on Done"), so observations die in a private thread. *Improvement:* point `FACTORY_DISCORD_WEBHOOK` (already supported as the ping override) at an open factory channel so Done arrivals, crashes, and prod-watch incidents are visible to everyone, inviting drive-by review of the pipeline itself.

## Section D — What the factory already does well

Genuinely covered strengths, so the audit isn't skew-negative:

- **One source of truth, done right** (factor 5): list = state, comments = verdicts; crash caps and bounce counts read back from the card so they survive daemon restarts ("Auto-start daemon", "Scheduler loop") — cleaner unification than many agent frameworks manage.
- **Structured verdicts drive deterministic control flow** (factors 1, 4, 8): the tagged-comment contract plus daemon logic means no LLM ever chooses a transition; bounces, parking, and the stuck-Verify routing are deterministic code.
- **Human contact is durable and multi-channel** (factors 6, 7, 11): `[ASK]` on the card + Discord ping + blocking/`--no-wait` wait + comment-resume with stage-aware recovery is a textbook outer-loop implementation, with fail-closed identity checks and watermark dedup (`scripts/lib/factory-comment-resume.js`).
- **Triggers from anywhere including machines** (factor 11): UI drags, human comments, and **production outages** all start/resume work — the outage-opens-an-investigation-card loop (`scripts/prod-watch.js`) is ahead of the blog's flow, which assumes humans or agents initiate changes.
- **Small, isolated, bounded work** (factor 10; blog theme B17): one agent per stage, one card per run, worktree isolation, `FACTORY_MAX_PARALLEL`, and per-run time/cost caps make blast radius structurally small.
- **Convergence cap by construction** (blog theme B13): the 3-bounce rule guarantees the agent↔agent loop terminates — the exact protection the blog had to add after a 50-round PR.
- **A real verify gate with a machine-readable verdict** (blog theme B10 half): `scripts/verify-deploy.js`'s JSON-verdict contract embedded into `[VERIFY:FAIL]` is precisely the "compact errors into context" pattern, applied where it matters most.
- **Rollback exists already** — `scripts/deploy.js` history-based rollback is built; the pipeline just needs to call it (C-H5).
- **Short owned instruction file** (blog theme B2 foundation): `AGENTS.md` keeps repo rules short and points to `docs/factory.md` for the full contract — the shape the blog recommends for `CLAUDE.md`.
- **Merge gate discipline** (blog theme B9 foundation): fresh-fetch + rebase + `mergeable` + always-`--ff-only` merges plus a post-merge integration test is a solid skeleton to grow a true merge queue from (C-M10).
- **Dependency-injectable, unit-tested factory libs** (`tests/factoryAsk.test.js`, `tests/factoryCommentResume.test.js`, `tests/factoryDaemon.test.js`, `tests/factoryDonePing.test.js`): the deterministic half of the factory is regression-protected, giving C-M11's eval loop a stable base to score agent judgment on top of.
