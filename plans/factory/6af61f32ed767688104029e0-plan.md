# Plan — 6af61f32ed767688104029e0 — GitHub PR as the mobile approval surface

**Card:** "Create a PR when a change need to be approved." — *"Or something
other than the SHA. I want a mobile friendly way to see what is changing when
a card needs human approval."*

## 0. Problem (verified against code, not vibes)

When the risk gate (`scripts/lib/factory-risk.js` `approvalGate`, CLI
`factory.js approve` → `scripts/factory.js:708-720`) hits a medium/high tier
it posts ONE `approvalAskText` (`factory-risk.js:83-89`) — tier + reasons +
the sha twice + reply rules — plus a Discord ping (`factory-ask.js`
`askHuman`/`sendOwnerPing`), then blocks for a human Trello comment
containing the sha (`findApprovalComment:216`, `shaMentionRe:193`).

Two defects the card names:
1. **No diff.** The human must `git diff` or open GitHub from a desktop to
   see *what is changing*. (`docs/factory-delta-migration.md` §5 states the
   same gap: "No diff … That is the card's complaint.")
2. **Typing a 40-char sha into a Trello comment on a phone** is the only
   approval gesture — the card says "Or something other than the SHA".

## 1. Chosen design: open a PR at the moment approval is needed

When the gate must ask, it **pushes the card branch and opens (or updates) a
GitHub pull request**, puts the PR URL in the `[ASK]` + Discord ping, and
**also accepts a GitHub PR review approval at the exact QA sha** as an
alternative approval gesture. The human opens the link on a phone → GitHub
app / mobile web shows the real diff (Files tab) → Review changes → Approve.
No sha typing, no desktop.

Why a GitHub PR beats the alternatives:
- **It is the card's own proposal** ("Create a PR when a change need to be
  approved"), and GitHub mobile is the best phone diff reader the human
  already has.
- **The box is already wired for GitHub:** remote
  `git@github.com-factory:Ajohnson-1/factory.git` via a write deploy key +
  `insteadOf` rewrite (`docs/factory-migration.md` §3 step 3); push verified
  2026-11-12 (`git ls-remote` OK; `factory/*` branches are local-only today,
  the gate's push creates them on demand).
- **`gh` CLI is NOT installed on the box** and needs a token anyway → talk to
  the GitHub REST API directly with global `fetch`, the established codebase
  pattern (`factory-ask.js` posts to Discord REST with bare `fetch`, every
  seam DI'd and faked). No new binaries.
- **Delta thread links** (`docs/factory-delta-migration.md` §5/§6) remain the
  richer long-term answer but are beta, need an unverified device-login on a
  headless box, upload code to a third-party cloud, and their Phase 0 spike
  has not run. A GitHub PR is first-party, ships now, and is exactly the
  "record + human-visibility surface" Phase 1 was going to provide. This
  plan adds a one-line cross-reference to the Delta study.
- **Posting the diff into Trello** (comment/attachment): raw diffs are
  unreadable on a phone and there is no approval affordance.

### Acceptance rules (fail-closed; board stays the source of truth)

The gate accepts EITHER source, never weakened:
1. **Trello sha-keyed human comment** — exactly today's rule, unchanged
   fallback (`findApprovalComment`).
2. **GitHub PR review approval** — qualifies only when the review is
   `state === "APPROVED"`, its `commit_id` equals the gate's sha
   (full sha, case-insensitive), and the reviewer login is in the approver
   allowlist (default: the repo owner parsed from the origin URL — so
   fail-closed single-approver with zero config; `FACTORY_GITHUB_APPROVERS`
   overrides). A review at any other commit never counts → a rebase re-keys
   the approval, the same stale-sha rule as the board path.
   `CHANGES_REQUESTED` is recorded in the result JSON, never approves.
   When the gate observes it, it posts a **mirror board comment**
   `[HUMAN] APPROVED <sha> — GitHub PR #<n> review approved by <login>` so
   the board shows the decision (comments are the state). The mirror is
   bot-authored and is ignored by the board scan (`findApprovalComment`
   drops bot comments) → no self-approval, no double-count; the GitHub
   source stays independently re-checkable on re-runs.
3. `--auto-approve` stays an in-run omp tool permission, never the human
   gate. Landing stays the scheduler's `merge --ff-only`.

### Everything PR-side is best-effort; everything gate-side stays strict

No token / `FACTORY_PR_APPROVALS=0` / push fails / API error ⇒ **zero
behavior change**: today's sha-only ask text, byte-identical, exit semantics
untouched; degradation is recorded in the printed result JSON
(`pr: { number, url }` or `pr: { degraded: true, error }`), never thrown,
never retried into a hang (bounded to the same poll cadence). A GitHub API
5xx during the wait degrades that cycle and self-heals next poll (the
`pollForReply` bot-identity precedent). Tier `low` ⇒ today's zero-board-write
fast path plus **zero GitHub calls** (the PR machinery runs only after the
low check).

## 2. Flow (medium/high only; low tier byte-identical)

1. Existing Trello sha approval scan → return (zero new writes) — unchanged.
2. **Best-effort `ensurePr`** (new `factory-pr.js`):
   - push: `git push origin <branch>`; on a non-fast-forward rejection (a
     merge-guard rebase rewrote the branch) → `git fetch origin <branch>` →
     `git push --force-with-lease origin <branch>`; still failing →
     degraded.
   - look up an open PR by head (`GET /repos/{slug}/pulls?state=open&head=<owner>:<branch>`);
     found & body keyed to a different sha → `PATCH …/pulls/{n}` body + one
     issue comment naming the new sha (re-ask after rebase is visible on the
     PR); found & same sha → reuse as-is; none → `POST …/pulls`
     `{ title: "<card name> (factory <id>)", head: branch, base: registry baseBranch, body }`.
     Body: tier + reasons, the QA sha, the numstat file table from
     `classifyDiff` (already computed — N files, +A/−D per path), the Trello
     card link, and the contract sentence: approving at this commit approves
     merge+Deploy of sha X; a later push requires a fresh approval; or reply
     on the card with the sha. Card title fetched best-effort via
     `t.getCard` (fallback title `factory/<id>`).
3. **Existing PR approval scan** (covers late-approve recovery: timeout →
   park → human approves the still-open PR on their phone → drag to Ready →
   the re-run's scan finds the review, mirrors, exits 0).
4. **ONE ask + ping** — `approvalAskText` gains one early line
   `Review the diff & approve from your phone: <prUrl>` placed inside the
   first ~180 chars so it survives the ping's 300-char brief truncation
   (`factory-ask.js:325`); no PR → today's text unchanged.
5. **Wait loop** — unchanged deadline/timeout/park semantics. With a live PR
   the single blocking `waitForHuman(remaining)` becomes bounded slices of
   `intervalMs`, and each cycle also runs the PR review check (2 authenticated
   GETs per 30 s — far inside rate limits). Without a PR the exact old
   single-call loop runs, preserving poll-count behavior. Wrong-sha replies
   AND wrong-sha reviews advance the window, never re-post the ask. Timeout
   → exit 1 → `needs-human` park, PR stays open for the late approve.
6. Merge path untouched; after the ff-merge + push master, GitHub marks the
   PR merged/closed automatically (head commits land on base) — verified in
   the canary, else a best-effort `close` on Verify.

   PR approval (recovery path proven).

## 8. Risks

- **GitHub API churn/format drift**: pinned `X-GitHub-Api-Version`, fail-closed
  parse (unrecognized review fields → no approval), degradation path.
- **A force-push clobbering a remote `factory/*` branch** — only the factory
  writes these refs; `--force-with-lease` only after a real ff rejection.
- **Reviewer approves, then branch moves**: GitHub keeps the old approval
  visible; our commit_id keying ignores it — correct re-keying by design.
- **PAT is personal-account-bound** — same trust domain as the Trello token
  already in `.env`; approver allowlist bounds who can approve.
- **`t.getCard` title fetch failure** → fallback title `factory/<id>`, body
  still carries every fact.
