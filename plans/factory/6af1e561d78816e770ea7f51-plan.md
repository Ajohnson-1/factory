## 1. Requirements (card description, verbatim intent)

Follow the four Warp docs and **create Cards** that add scorers, benchmarks,
and self-improvement loops to this factory:

- https://docs.warp.dev/factories/measure-and-improve/ — Dashboard metrics
  (runs/PRs/autonomy/cycle-time/cost-per-PR/scorer cards/self-improvement
  PRs) + the practical improvement loop: define a Scorer → collect a
  baseline → inspect failures → benchmark a candidate → review and adopt →
  keep monitoring.
- https://docs.warp.dev/factories/measure-and-improve/scorers/ — a Scorer is
  an LLM judge that classifies completed runs against written criteria:
  fields = agent(s), judge instructions, judge model, classifications
  (label→score), pass threshold, sample rate; automatic scoring at the
  sample rate plus on-demand single-run scoring; re-scoring replaces the
  prior result.
- https://docs.warp.dev/factories/measure-and-improve/self-improvement/ —
  repeated Scorer failures (score < pass threshold) get grouped per agent
  and turned into follow-up PRs (default trigger: 25 distinct unreviewed
  failures or oldest ≥ 7 days); each follow-up PR carries a "Regressions
  addressed" section linking the failing runs; fixes may target application
  code or the factory definition itself; nothing adopted without review.
- https://docs.warp.dev/factories/benchmarks/ — a benchmark suite is a
  reusable task collection for one agent; tasks carry a prompt +
  "Correctness criteria"; launches compare configurations (model/harness/
  runner) × repetitions; results = per-configuration scored-trial
  comparison + overall recommendation; suites/tasks live as files
  (`benchmarks/<suite-slug>/suite.yaml`, `tasks/<task-slug>.yaml`) so an
  adopted change is reviewable as definitions-as-code.

Every created card: title prefixed `M&I`; description carries the step, its
sub-steps, its gates, and its outcomes.

## 4. Design decisions

1. **Five cards, ordered M&I-1 → M&I-5**, each independently runnable in the
   normal pipeline; dependencies are stated in descriptions and honored by
   the human who drags a card from To Do to Ready. Creation order 1→5
   preserves list order (Trello appends new cards to the bottom).
2. **All five land in `To Do`, never `Ready`** — the daemon polls only
   Ready, so nothing auto-dispatches; the human releases them one at a time
   (one-card-in-flight canary posture).
3. **JSON, not YAML** for scorer/benchmark files. `package.json` has zero
   runtime dependencies (devDep `jest` only); adding a YAML parser for two
   file types is unjustified. Warp's `scorers/<name>/scorer.md` and
   `benchmarks/<suite>/suite.yaml` map to `scorers/<name>.json` and
   `benchmarks/<suite-slug>/suite.json` + `tasks/<task-slug>.json` — the
   "definitions as reviewable files in git" property is what matters, not
   the extension.
4. **New `[SCORE:<scorer>]` verdict comment is bot bookkeeping** (class of
   `[METRICS]`/`[PROD-CLOSE]`/`[RESUME]`): never bounce-counted, never a
   gate; the Board-contract tag list in `docs/factory.md` is updated in the
   same card (the `tests/factoryStagePrompts.test.js` doc-sync test keeps
   docs and code honest). No new scheduler routing.
5. **LLM spawns cost money** (the metrics report measures exactly this):
   scoring/bench runs are explicit-invocation or opt-in-sample only, with
   dry-run zero-write modes and hard per-run limits — every existing
   precedent (`eval-run` "no CI job runs it", metrics' zero-spawn design,
   `FACTORY_MAX_COST`) is followed; no card may wire an LLM spawn into the
   daemon poll loop unconditionally.
6. **Reuse, don't fork:** judge spawn/parse through `scripts/lib/factory-eval.js`
   helpers (extract shared code rather than copy); watermarks use the atomic
   temp+rename JSON files of the blocking-checks precedent; card filing uses
   `add` + `desc` (prod-watch/sweep machine-written-requirements precedent —
   agents never edit the description); failure grouping reuses the
   prod-close layer enum; dedup uses the seed-audit rule (exact trimmed title
   match against ALL open board cards) plus the sweep date-title rule.
7. **This card changes no code.** Its deliverable is the five board cards +
   `plans/factory/6af1e561d78816e770ea7f51-cards.md` recording what was
   created. Diff = `plans/**` → tier low → zero approval friction. Each M&I
   card then rides the full pipeline as its own card.

## 6. Creation mechanism + idempotency (the implementer's recipe)

All commands run from `/opt/factory` (the runtime clone), CLI invoked as
`node /opt/factory/scripts/factory.js …`, and **board/list commands carry
`--repo factory` AFTER the command** (§2 — flagless defaults to the
discord-bot board; a leading flag errors). `desc` takes NO flag (positional
args are the description text).

0. Snapshot the board once (the seed-audit dedup source):
   `node /opt/factory/scripts/factory.js status --repo factory > /tmp/mi-board.json`
1. For each planned title in M&I-1..M&I-5 order: **skip iff** the exact
   trimmed title already appears among `status.lists[].cards[].name`
   (seed-audit rule — ALL open board cards, so a card a human already
   dragged to Ready/Plan is never duplicated). Skip ⇒ record it as
   `existing: <id>`; do NOT create. This makes a bounce re-run create 0.
2. Create: `node /opt/factory/scripts/factory.js add To Do '<exact title>' --repo factory`
   → parse `{id,url}` from stdout. Titles are single-quoted (the `&` is literal).
3. Describe: write the §5 fenced block byte-for-byte to `/tmp/desc-mi<N>.txt`
   (heredoc with QUOTED delimiter — `<<'EOF'` — so `$`, backticks, `%` stay
   literal), then `node /opt/factory/scripts/factory.js desc <id> - < /tmp/desc-mi<N>.txt`.
   Verify stdout `{updated:true, chars:<n>}` with `chars` matching
   `wc -c /tmp/desc-mi<N>.txt`.
4. If a run dies mid-way, the watermark-less retry is safe: step 1's dedup
   sees already-created titles (names are exact constants in §5) and re-runs
   create/skip correctly. No state file needed — the board is the state.
5. Do NOT move any card, do NOT touch other cards, do NOT edit this card's
   description; no `label` calls (priority is conveyed by the M&I-N order).
