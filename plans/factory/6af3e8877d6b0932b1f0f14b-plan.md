# Plan — 6af3e8877d6b0932b1f0f14b "Look in to moving repos to delta"

Card requirements (verbatim intent): what it takes to move the repos' agent runs to
Zed Delta (https://zed.dev/blog/delta-public-beta) **and keep a gate when human
approval is needed**, with the human able to *see what is changing* when that gate
fires.

**Verdict:** "Moving repos to delta" is not a flag swap — Delta is not a headless
one-shot agent CLI like `omp -p`. The delta CLI records/shares conversations and
worktrees; it does **not** run turns from a script (see §2). The plan is therefore a
phased migration: **keep `omp -p` as the runner and the Trello board as the gate's
authority; add Delta as the record + human-visibility surface** (Phases 0–2), and
defer delta-native execution (Phase 3) until Delta exposes a documented CLI trigger
for hosted runs. Every phase leaves the sha-keyed approval gate, the ask protocol,
and the git `--ff-only` merge flow untouched — the gate never moves to Delta's
review verdicts; Delta only makes the diff visible and (optionally, Phase 2b)
attests approvals into the board flow.

All file:line cites are against `origin/master` 8372b95 (this branch's base).

---

## 0. What Delta is (facts the plan is grounded in)

Sources: the card's blog post + Delta docs (beta banners say commands/flags/output
can change — https://delta.dev/docs/cli/get-started).

- **Threads replace PRs** as the unit of collaboration: conversations with agents +
  worktrees; review happens in dedicated review subthreads whose agent produces a
  "change guide"; a human submits a verdict **Approve / Request Changes** from
  desktop **or web** (`/approve`, `/request-changes`) —
  https://delta.dev/docs/agents/review-and-sync. The **Changes tab** shows the real
  diff vs an upstream ref "since the merge base" (e.g. `origin/master`), with
  per-file Seen tracking; the merge base is recorded and shared with everyone
  including web viewers. Landing is still Git: "pushing to `local` or your source
  remote" is what brings work in; commits remain the checkpoints
  (https://zed.dev/blog/delta-public-beta, review-and-sync §Bring changes in).
  → Git-flow gates (merge-base diffs, shas) survive a Delta migration intact.
- **The CLI cannot start an agent run.** `delta thread create` can seed a
  `--prompt --model` *draft* but "Nothing runs until someone sends the draft"
  (get-started §Start a thread from a checkout); `thread append` "records activity.
  It doesn't run messages or tool calls"
  (https://delta.dev/docs/cli/build-a-plugin). The documented scripting model is a
  **plugin**: your agent keeps running on your own harness (like
  `delta-claude` does for Claude Code) and the CLI mirrors its ACP-v2 transcript and
  worktrees into a thread (`thread create --source/--external-id`,
  `worktree create/attach/mount --existing-checkout`, `thread append` JSONL,
  `thread watch` JSONL, `thread stop`, `thread contract` version handshake —
  contract v8 on Delta 0.22.0). This is the exact seam the factory plugs into.
- **Auth/install:** CLI runs on the Delta app (`~/.local/delta.app` on Linux,
  `~/.local/bin/delta`); device-code login (`delta auth login`; the CLI machine
  needs no browser), `delta auth status` exits 0/1/2; account + organization
  scoped (`delta org create/list/switch`); usage telemetry tied to the account.
  No API token is documented → a server-side service identity story is an open
  question (§6).
- **Worktrees:** `worktree mount --existing-checkout` uploads the checkout
  *including uncommitted changes* and keeps syncing while the process runs;
  `thread mount` creates mount checkouts for joiners. "Local Git state, such as
  branches, aren't shared or kept."
- **Execution surface:** hosted threads run in the Delta app / a "Cloud Runner"
  (mentioned only in passing, thread-delete section); no CLI command to trigger or
  await a hosted turn is documented. Phase 3 hinges on this.

## 2. Where the human-approve gate lives today, and exactly what changes under delta

**Today (unchanged by this card's migration in every phase):**

- Gate call: after `[QA:PASS]`, before `git merge --ff-only`, from the card
  worktree: `node scripts/factory.js approve <card> <sha> factory/<id>`
  (`scripts/factory.js:708-720`; prompt step `scripts/factory-daemon.js:268`;
  spec docs/factory.md `:894-977` "Risk-tiered approval before Deploy").
- Tier classify is pure git: `getDiffStat` (`scripts/lib/factory-risk.js:165`,
  merge-base numstat) → `classifyDiff` (`:102`); low → exit 0, zero board writes.
- Medium/high: scan comments for an existing **sha-keyed human approval**
  (`findApprovalComment` `:216` — author ≠ bot OR `[HUMAN]`-tagged and non-bot;
  bot-authored NEVER counts; sha regex `:193`); none → ONE `askHuman({noWait:true})`
  posting `approvalAskText` (`:83-89`) + Discord ping, then `waitForHuman` polling
  until `approvalTimeoutDefault()` (`:77`: `FACTORY_APPROVAL_TIMEOUT_MS` →
  `FACTORY_ASK_TIMEOUT_MS` → 1 h) → timeout ⇒ `{approved:false,timedOut:true}` ⇒
  CLI exit 1 (`factory.js:719`) ⇒ scheduler labels **needs-human**, card stays in
  QA, no merge, **park not bounce** (bounce budget untouched); recovery = approve
  late on the card + drag back to Ready, the re-run's existing-approval scan
  short-circuits — "comments are the state".
- The comment-resume watcher (`scripts/lib/factory-comment-resume.js:342`
  `isAskPending`, guardrail at `:765`; docs/factory.md `:1361-1489`) keeps silent
  while the gate owns the reply; a human **drag past the gated stage** is itself a
  complete approval decision.

**What the human sees today when approve is needed:** the `[ASK]` comment text —
tier + reasons (paths/churn counts), the sha twice, reply instructions, stale-sha
rule (`factory-risk.js:83-89`) — plus a Discord ping. **No diff**: the human has to
`git diff` / open GitHub themselves to see *what is changing* — that is precisely
the card's complaint.

**What changes when approve is needed under delta (Phases 1–2):**

1. The `[ASK]` gains a **Delta thread link** (the card's run's thread, shared to
   the org). Tapping it opens the thread on web/mobile: the **Changes tab** shows
   the live diff of the card's worktree vs `origin/master` since the shared merge
   base, with per-file Seen tracking; a review thread shows the change guide
   (review-and-sync docs, cited §0). *This is the whole "I'd like to see what is
   changing" answer — additive, gate logic untouched.*
2. The Discord ping carries the same link.
3. Delta's own approval surface (review-thread **Approve / Request Changes**
   verdicts, web-capable) becomes a *second, richer* place to look — **but it must
   NOT bypass the board gate**: in Phases 0–2 `approvalGate`
   (`factory-risk.js:256-343`) still accepts only a sha-keyed Trello human comment
   (or a stage drag); a Delta verdict is advisory. Phase 2b may add an *attested*
   path (§4) behind an env flag, because bot-authored comments never count
   (`:216` criterion 3) — a mirror bot cannot fake the human on the board.
4. Timeout/parking/needs-human semantics, sha keying (`shaMentionRe` `:193`),
   rebase-requires-new-approval (`merge-guard` re-gate, prompt `:268`) are
   unchanged — `approve` still keys the git commit sha, and Delta keeps commits as
   checkpoints (blog), so the sha anchor survives the migration.
5. `--auto-approve` (omp flag, `agentArgs:279`) stays what it always was: an
   in-run tool-permission accept, never the human gate.

## 3. Phased migration

### Phase 0 — spike on the Proxmox box (no code)
Install Delta CLI headless (`curl -fsSL https://delta.dev/install.sh`; Linux →
`~/.local/delta.app`, CLI at `~/.local/bin/delta`), then prove, with one real card
worktree:
- CLI works with no GUI session (the CLI "starts the app in the background" —
  verify on the headless box; troubleshooting doc if not),
- `delta auth login` device flow from ssh + `delta auth status` survives reboot,
- `delta --json thread contract` reports contract ≥8 (fail-closed version gate,
  like the plugin doc's handshake),
- `thread create --source factory --external-id <card>` +
  `worktree create/attach/mount --existing-checkout` + `thread share --visibility
  organization` → the human opens the share URL **on a phone** and sees the live
  diff vs `origin/master`,
- rebase/merge-gate git ops on the branch while mounted (`--existing-checkout`
  syncs uncommitted state; verify the merge-gate rebase at prompt step `:268` does
  not fight Delta sync),
- org setup: `delta org create` / `org switch`; decide the factory service account
  vs personal account (open question §6).
Exit criteria: gate `[ASK]` text written by hand with a thread URL → the human
reviews the diff from their phone in <2 min. Record results in
`docs/factory-migration.md` §9 cutover log style.

### Phase 1 — Delta sidecar: record + approval visibility (the recommended default)
Runner stays `omp -p`; every dispatch/resume run gets a Delta thread mirroring its
worktree, and the approval ask carries the thread link.

Files:
- **`scripts/lib/factory-delta.js` (new)** — DI like the factory-ask/factory-risk
  pattern: `ensureThread({cardId, repo})` → idempotent `thread create` (same
  `--source/--external-id` returns the same thread — plugin doc), `worktree
  create/attach/mount` child (stdio → the card's daemon log), `thread share` →
  `{threadId,url,mountPid}`; `stopMount`; best-effort throughout (failure ⇒ null ⇒
  pipeline continues — the sendOwnerPing precedent). Reads per-repo delta config.
- `scripts/factory-daemon.js` — `dispatch()` `:746-789` + `spawnResumeRun()`
  `:792-816`: ensure/attach thread, track `{child,mount}` in `runs`, SIGTERM the
  mount in `shutdown` (`:818-831`); write a **separate** `# delta <ISO> <threadId>

  `parseDispatchHeaders` `factory-metrics.js:497` `JSON.parse`s everything from
  the first `[`, trailing junk silently drops the cost cap; a separate line keeps

- `scripts/lib/factory-risk.js` — `approvalAskText` `:83-89` gains an optional

- `scripts/factory.js` — operator command `delta-share <card> <path>` (manual

Effort: ~1 card (library + wiring + tests), then a follow-up card if the verdict

### Phase 2 — transcript + comment mirroring (optional)
- 2a: `factory-delta.js` records coarse run activity as ACP-v2 `thread append`
  records (dispatch header, stage verdict comments, final state; JSONL contract
  v8, `--acknowledge local` for offline box resilience) and runs a `thread watch`
  sidecar per live run to mirror **human thread comments** back as Trello comments,
  so the comment-resume watcher (docs/factory.md `:1361`) keeps working unchanged —
  the board stays the single source of truth.
- 2b (flag-gated, `FACTORY_DELTA_APPROVALS=0` default off): poll the card thread's
  review verdicts; an **Approve** submitted by a whitelisted Delta user on the
  thread whose `external-id` is the card and whose verdict snapshot commit matches
  the QA sha is *attested*: the factory posts
  `[HUMAN] APPROVED <sha> (delta-review verdict by <user>)` and extends
  `findApprovalComment` (`factory-risk.js:216`) with an injectable `attested`
  source (`via:'delta-verdict-<user>'`). Doc change in "Gate protocol" required
  (the bot-authored rule gets one named, verified exception; every other bot
  comment still never counts).

### Phase 3 — delta-native runs (exploratory; blocked, do not schedule)

(hosted agent / Cloud Runner). Known blockers before it can even start:

- headless service identity (personal-account-bound device login);
- run-lifecycle translation: exit codes/`runs` map/`FACTORY_MAX_PARALLEL` cap →

  `delta thread show --format messages` transcripts instead;
- stage subagents → Delta subthreads/subagents: `buildRunPrompt` `:256-275` +
  all five `docs/factory-prompts/*.md` + `tests/factoryDaemon.test.js:115-119`

Files touched: essentially `scripts/factory-daemon.js`, `scripts/lib/{factory-comment-resume,factory-stall-sweep,factory-eval,factory-metrics,factory-delta}.js`,

## 5. What explicitly does NOT change (the gate contract survives delta)

Board pipeline + stage tags; risk-tier classification (pure git numstat); sha
keying (`shaMentionRe`, rebase ⇒ new approval); human-reply author rules; ask
protocol + timeout + `needs-human` parking (park, never bounce); comment-resume
drag-as-approval; `git merge --ff-only` landing on `origin/master` (Delta is
Git-compatible; the merge/merge-guard steps are ordinary git); Trello remains the
source of truth for stage state and approvals in every phase.

## 6. Risks + open questions

1. **No CLI-triggered hosted run** (facts §0): delta-native automation is
   impossible today; Phase 3 stays exploratory until the roadmap/API says
   otherwise. If Zed never ships it, Phases 0–2 are the end state — which already
   answers the card (gate stays on the board; the human sees the diff in Delta).
2. **Beta churn**: commands/flags/output "can change between releases"; mitigate
   with the `thread contract` handshake (pin v8) + fail-closed enrichment; the
   pipeline must never depend on Delta availability.
3. **Headless box**: CLI runs on the Delta app; GUI-less operation + login
   persistence are unverified (Phase 0 decides; a `delta auth status` pre-dispatch
   health check goes in the daemon if login can expire).
4. **Service identity**: device login binds a personal account; an org service
   account / future API token is an open question. Threads + file contents upload
   to Delta cloud (org members can read shared threads; telemetry on by default,
   account-tied) — acceptable for these repos? Decide before Phase 1 canary.
5. **Mount vs merge-gate**: `--existing-checkout` syncs uncommitted work while the
   scheduler rebases the same branch (`:268` step); verify no fighting (Phase 0
   test), else share only committed state per stage.
6. **Verdict bypass risk**: Delta Approve must never merge/land on its own —
   landing stays the scheduler's `merge-guard` + `merge --ff-only`; docs state
   verdicts are advisory until 2b, and 2b is flag-gated + whitelisted-user.
7. **Doc/code tension to fix while in there**: docs/factory.md "Asking a human →
   Approval grammar" (`:761-828`, "reply matching is by AUTHOR, never by SHA") vs
   "Gate protocol" (`:925+`) and code (`factory-risk.js:216` requires the sha
   mention for *gate* approvals). The code is right (gate = sha-keyed; bare
   `Approved` qualifies for plain asks / resume-drags); amend the grammar wording
   in Phase 1's docs edit.
8. Cost/time guards: no `--max-cost`/`--max-time` equivalent on the Delta side;
   Phase 1 runs are still omp-bounded (unchanged), Phase 3 must re-invent the
   bounds — open.
9. Concurrency: Phase 2's per-run `thread mount` + `thread watch` sidecars add
   long-lived processes per card under `FACTORY_MAX_PARALLEL` — bounded by the cap,
   but the daemon `shutdown` (`:818-831`) must TERM them or sync hangs orphaned
   ("a mount whose process is gone doesn't keep Delta running" — acceptable
   degradation, but checkouts linger; cleanup command needed).
10. Open: which org/visibility per repo (`config/factory-repos.json` delta block —
    `organization` share exposes code to every org member; `private` + invites per
    card is the alternative).
